# 正文写作模块

状态：accepted

> 本提案记录开发者在 2026-09-28 至 2026-09-29 的讨论中确认的正文写作模块方向，作为 `docs/specs/writing/` 各份 `planned` Spec 的批准依据。它不宣称功能已经实现。

## 问题

大纲规划模块已经能在大纲库中产出正式采用的章节大纲和已审阅细纲，并通过只读交接（[outline.writer-handoff](../specs/outline/writer-handoff.md)）提供写作所需的上下文，但项目里没有把细纲写成正文的模块。现有 `writer` Profile 服务于 Plot、Writer Brief 与 World Engine，不读取大纲规划的正式内容；它的文风、人称、字数等设置与细纲里已有的写作指导、段落标注重复。

直接让单个 Agent 读完细纲和全部资料再写整章，存在三个可观察问题：资料会把写作者带偏或让它自行补剧情；伏笔背后的设计会被提前写出来；一章写完后前后段落不连贯，也无法定位哪一段没有写到细纲要求。

## 目标与非目标

### 目标

1. 在工作台里提供独立的写作界面：左栏映射大纲与正文，中间显示内容，右栏是按章节划分的写作会话。
2. 用“助手与作家系统”写正文：主创对接用户，助手读取资料并组装结构化提示，写手只按提示写作。
3. 能从源文件截取的内容一律由程序截取，模型只填需要判断的字段，防止二次转述带来的信息偏差。
4. 按场景逐段写作与审阅，每段都带着已通过的正文，保证全章连贯。
5. 正文记录所依据的规划版本，规划变化后可见“依据已过期”。
6. 写作中发现的规划缺口能回到大纲工作台处理，写作模块自身不改规划。

### 非目标

- 不改写大纲规划数据，不做剧情决定。
- 不维护伏笔账本，不读取伏笔定义正文。
- 不沿用现有 `writer` Profile 的设置项，也不改造现有 `writer` Profile。
- 不为多个大纲方案各写一份正文。
- 不自动合并用户手改与重新生成的正文。

## 当前行为与证据

- 规划侧已有只读交接查询并有测试，但它按线路读取：要求线路 id，只返回固定线路上的有效节点，伏笔按线路格号判定有效性（`packages/neuro-book/server/outline/writer-context.ts`）。本模块改为按大纲库层级读取，这部分需要替换，见 [outline.writer-handoff](../specs/outline/writer-handoff.md) 的实现合同。消费方尚未开发。
- 正文沿用项目的 `manuscript/` 目录与 `volume`、`chapter` 两种条目类型（`packages/neuro-book/server/workspace-files/workspace-files.ts`）。正文文件头已有的 `chapter:` 字段指向旧 Plot 系统的章节，与本模块无关。
- 工作台已有视图描述注册表、左栏活动栏按容器生成入口、右栏预留容器；目前只有“文件”视图接入（`packages/neuro-book/app/utils/workbench/product-catalog.ts`）。
- 主应用已接入 `nb-workflow`，具备 Agent 调用、运行记录重放、等待与取消（`packages/neuro-book/server/agent/workflow/`）。
- 细纲的段落写作指导带结构化的 `words` 与 `perspective`；章节级人称只存在于自由文本 `writingGuidance` 中（`packages/neuro-book/server/outline/format.ts`）。

## 方案、备选方案和取舍

| 议题 | 采用 | 放弃的备选与原因 |
|---|---|---|
| 界面形态 | 工作台视图：左栏“大纲”容器（活动栏新增入口），中间编辑器显示内容，右栏“写作”会话 | 全屏对话框：与正文编辑器割裂，看正文要切走 |
| 会话 | 嵌入会话，复用现有 Agent 会话界面，一章一个会话 | 面板加一键生成：无法沟通和局部修改；另拼一套会话组件：会与主 Agent 界面分叉演化 |
| 章节来源与顺序 | 以大纲库中写作方案的层级为准：卷纲顺序、卷内章节顺序即正文章节顺序；章节大纲已采用且细纲已审阅即可写 | 以固定线路为入口和顺序：线路规划暂时只供用户梳理剧情，不作为写作输入 |
| 左栏范围 | 按写作方案显示完整的卷、章节、细纲树和各章正文，不可写的章节灰显并标原因 | 只列可写章节：看不到全貌 |
| 左栏编辑 | 大纲只读映射；正文可在中间编辑器直接修改 | 在左栏改大纲：会出现第二条规划写入路径 |
| 正文与方案 | 作品选定一个写作方案，一章一份正文 | 每个方案一份正文：目录和状态复杂度成倍增加 |
| 依据记录 | 写在正文文件头 | 写回大纲文件：违反写作模块不写规划的边界 |
| Agent 组织 | 主创、助手、写手三个角色 | 单个 writer Profile：上下文混杂，资料与伏笔易泄露进正文 |
| 字段来源 | 程序从源文件截取细纲原文、写作指导原文、伏笔标记、字数、文风、正文片段；助手只填效果要求、写作手法、背景知识、必须写到的要素和审阅结果 | 助手转述细纲：二次输出会产生偏差 |
| 摘录 | 助手只提交“文件 + 位置”，程序取原文 | 助手复述摘录：同上 |
| 循环推进 | 程序按场景推进“写一场、审一场” | 助手推进：顺序和完整性依赖模型自觉，中断后难以准确续写 |
| 主创核对 | 核对一次场景规划；之后格式由程序校验，主创只在审阅不通过或偏离细纲时介入 | 每个场景都核对：场景数多时轮次和成本线性增长 |
| 文风 | `lorebook/instruction/` 下的写作风格文件，由程序解析后写进写手提示词 | 沿用 `writer` Profile 的文风预设：与作品数据分离，且该 Profile 已不使用 |
| 改写 | 程序截取目标段落和上下各两个完整段落，写手重写，用户看新旧对照后确认替换 | 直接覆盖：用户无法判断改动 |

## 数据、接口、安全、迁移、发布与回滚影响

- 新增的持久化数据：正文文件头的写作依据记录、作品写作设置、写作问题记录、写作运行记录。都保存在 Project 内，作为可审查的产品数据。
- 新增一种 instruction 条目：写作风格文件。
- 三个新 Profile（主创、助手、写手）与一个写作工作流。写手没有任何工具；三个角色都没有写文件的工具，文件写入全部由程序完成。
- 助手只读规划交接内容与资料，不读伏笔定义。
- 不迁移旧数据，不改现有 `writer` Profile；回滚时移除新视图、新 Profile 和工作流即可，已写出的正文文件保留为普通章节文件。
