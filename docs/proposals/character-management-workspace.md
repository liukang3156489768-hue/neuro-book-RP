# 角色管理工作区与可移植 Demo

状态：reviewing。数据与权限原则已由开发者确认；界面先通过独立 Demo 评审，正式项目接入尚未授权。本文件记录新页面的设计决定，不表示产品已实现。

## 问题与范围

角色资料需要独立的全工作区管理页面，以同时查看角色列表、基础信息、原作资料及不同改编方案的资料。后续还需重构角色提取产物和跨模块读取方式，本轮只交付设计文档与可运行的可移植 UI Demo。

文件继续是唯一可信来源。Demo 使用内存样例文件，不调用真实作品 API、不改变运行中的活动栏、不迁移角色、不调用模型。页面刷新会恢复样例。

## 已确认决定

2026-10-07，开发者确认：

1. 页面默认只读，通过明确的编辑按钮进入编辑状态；未保存内容为临时草稿。
2. 角色图片放在对应角色目录，Markdown 仅保存相对于该角色目录的图片路径。
3. 新读取目标为单个项目容器根下的 `lorebook/character/`，角色提取也继续写入该目录；不兼容本次重构前的旧角色产物。正式接入时须同时调整提取和消费者，不能仅切换 UI 搜索路径。
4. 正常列表仅展示具有有效 `index.md` 的正式角色。缺少入口文件的目录进入资料异常视图。
5. 用方案标签区分各方案产生的角色侧面；文件使用方案文件夹隔离。
6. 原作经历与关系在本页面只读，只能通过底层文件编辑或重新提取修改。
7. 文件结构预留原作知识和各改编方案中的知识，两者分别存储、分别读取；本轮角色提取不生成知识文件，知识由写作与剧情规划按需维护。
8. 文档完成后先做 Demo，开发者确认后才实装。

## 界面设计

入口位于左侧活动栏的文件与大纲之间，名称为角色。点击后以嵌入式页面占据活动栏外的工作区，不使用弹窗。复用现有角色入口的身份，正式接入时替换旧视图，避免两个入口并存。

桌面使用三栏，左栏约 280px、中栏为主要伸缩区、右栏约 410px。每栏独立滚动，标题和操作区保持可达。低于三栏所需宽度时，以角色列表、基础信息、经历关系三个导航项切换；390px 下无横向页面滚动。

### 左栏

搜索名称、别名与标签，支持标签筛选、名称排序和正常／资料异常切换。列表和卡片共用稳定角色 ID。列表显示姓名及标签；卡片为矩形图片，标签位于右上角，姓名位于下方。没有图片使用首字占位，不默认伪造角色肖像。

上方方案标签决定当前查看的角色侧面。基础／原作标签展示所有正式角色；方案标签展示该方案已有资料的角色。无匹配结果显示明确空状态，清空筛选可以恢复。

### 中栏

身份：姓名、别名、标签、基本身份、摘要。

设定：外貌、穿着、家庭情况、经济情况、特殊能力、性格、性格描述。

正文状态：上次出现的章节及位置、持有物品、心理状态。状态从当前方案的状态文件读取；基础人设不随切换方案被覆盖。基础／原作视图显示原作状态，改编方案显示方案状态，未记录时明确显示未记录。

基础信息与图片通过编辑、保存、取消维护。名称必填，图片必须是可解码的受支持图片。保存失败保留草稿；切换角色、方案、视图或刷新样例前，存在未保存修改时提供保存并继续、放弃修改、继续编辑三种选择。

### 右栏

一级导航为原作资料和当前方案资料；原作资料始终可以查看，切换到原作不会改变方案选择。

二级导航为经历、关系、角色知识。原作资料只读，显示来源文件及打开底层文件入口；Demo 的该入口仅展示样例 Markdown。

当前方案资料允许编辑已有记录或新增记录，保存至对应方案目录。关系以稳定目标角色 ID 关联，只允许选择既有角色；不在此流程新建角色。知识记录区分已知内容、未知内容／信息差、误解和信息来源，避免将模型知道的全部信息等同于角色知道的信息。

## 候选文件合同

以下是供 Demo 展示和后续正式接口设计的候选结构，尚未修改产品 schema：

```text
<project-container>/lorebook/character/<character-id>/
├── index.md
├── avatar.png
├── original/
│   ├── experience.md
│   ├── relationships.md
│   ├── knowledge/
│   │   └── index.md
│   └── state.md
└── plans/<outline-plan-id>/
    ├── experience.md
    ├── relationships.md
    ├── knowledge/
    │   └── index.md
    └── state.md
```

角色 ID 和方案 ID 是稳定目录身份；名称与方案名称仅用于显示。每个侧面文件保存该侧面的全部记录，避免每条经历产生一个小文件。缺少某个侧面文件表示该类别尚未记录，不表示角色无效；缺少 `index.md` 才进入资料异常。

`knowledge/` 分别位于原作目录和方案目录，入口文件保存该侧面的角色已知事件、已知信息、未知信息及误解。读取原作知识不会自动复制或混入方案知识。

`index.md` 使用已有 `title`、`aliases`、`tags` 和 `ext.character.profile` 的概念。基础提取模板严格对齐角色页面字段，包含摘要、身份、外貌、穿着、家庭、经济、能力、性格和性格描述／气质；新增家庭、经济字段以及 `ext.character.meta.avatar`。实际 schema 校验及 DTO 扩展留待正式接入，Demo 不声称现有 DTO 已具备这些字段。角色引用允许输入显示名称或别名，解析后统一落到稳定角色 ID。

基础人设不被改编规划 Agent 覆盖。角色页面中的人工编辑属于明确的文件编辑能力；方案信息与原作信息分别维护。原作知识与经历／关系一样在页面只读，保证原作资料整体具有一致的来源边界。

## 现有接口与接入边界

- [旧角色详情组件](../../packages/neuro-book/app/components/novel-ide/workspace/WorkspaceCharacterDetailPanel.vue)：参考基础资料展示，不沿用其旧目录读取方式；该组件目前没有同名契约文档。
- [现有角色 DTO](../../packages/neuro-book/shared/dto/character.dto.ts)：支持 `CharacterProfile`、`CharacterStory`、`CharacterMeta`；本轮不修改。
- [文件读取接口](../../packages/neuro-book/server/api/workspace-files/read.get.ts)：接入时携带当前项目身份和项目内相对路径。
- [文件保存接口](../../packages/neuro-book/server/api/workspace-files/write.put.ts)：接入时沿用 `expectedMtimeMs`、`baseContent` 的版本冲突合同，不能无条件覆盖外部修改。
- [文件上传接口](../../packages/neuro-book/server/api/workspace-files/upload-file.post.ts)：目前默认上传到 upload/，不能直接当作角色头像上传接口使用；正式接入需要验证角色目录的独立图片写入能力。

Demo 将视图与读写分开：宿主提供角色投影、方案列表、保存基础资料、保存方案资料、选择图片、打开文件能力；可移植 Vue 视图不读取 store、项目路径、浏览器持久化或真实 API。正式接入时替换样例宿主即可保留页面交互，仍需实现上述文件适配边界。

## 数据、迁移与回滚影响

不提供旧角色兼容或自动迁移。正式切换须同步角色提取、大纲规划、设计工作台、写作资料补充与审核、路径解析和角色引用；既有提取结果需按新格式重新生成。2026-10-08 已清除当前测试项目 `lorebook/character/` 下的旧角色提取目录，仅保留类别根目录文件。其他项目在正式切换时同样需要重新提取，不执行自动迁移。

正式实现前应把批准后的行为整理到角色 capability 的单一 planned Spec；本轮不将 Demo 标记为 implemented，不修改已有 Spec 的当前行为。

## Demo 验收

检查活动栏位置、三栏滚动、列表／卡片切换、搜索与标签筛选、方案资料隔离、原作只读、基础资料与图片保存／取消、方案记录编辑、未保存离开提示及390px 布局。仅验证样例交互，不代替真实文件写入、冲突检测、提取和模型验收。
