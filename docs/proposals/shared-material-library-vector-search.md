# 跨小说项目共享素材库与向量检索

状态：draft。记录日期：2026-10-03。本文作为后续可能采用的优化灵感保存；开发者仅要求记录设想，未批准实施、迁移数据或改变当前产品合同。

## 问题

素材提取会产生大量写作手法与素材特点条目。当前通过项目内分类目录和两份 Markdown 索引管理，已经改善 note 根目录混乱的问题，但仍有两个长期使用问题：

- 条目持续增加后，让写作 AI 每次浏览全部索引或正文会占用较多上下文，需要根据当前写作需求找到少量相关素材。
- 写作手法与可借鉴的素材具有跨作品使用价值；如果只在提取它们的小说项目内可用，其他小说就难以复用。

开发者明确提出：写作手法与素材本身不应受单个小说项目限制，借鉴其他作品的设定和写法也是有效的创作方式。

## 目标与非目标

目标设想：

- 建立同一用户数据空间内、可供多个小说项目使用的共享素材库，首期考虑写作手法与素材特点两类。
- 让 AI 按写作需求检索摘要与候选条目，再按需读取正文，减少无关内容进入上下文。
- 保留来源信息，允许按类别、来源作品等过滤；来源项目不作为默认必须满足的检索条件。
- 保持小说正文、人物状态、剧情进度及提取草稿的项目隔离边界。

本文不安排实施，不改变现有提取写入路径，不迁移历史文件，不启动真实 Embedding 调用；多用户共享、跨设备同步与外部素材市场不属于本次设想范围。

## 当前行为与证据

以下为源码核实结果，未验证运行时 Embedding 配置或真实检索效果：

- [素材提取规范](../specs/inspiration/material-extraction.md#写作手法与写作素材的检索索引)：正式内容位于项目的 `lorebook/note/写作手法/` 和 `lorebook/note/写作素材/`；note 根目录保存两份带分类、摘要、检索词与实际文档链接的索引。正文不跨块整合。
- [SQLite 向量适配器](../../packages/neuro-book/server/rag/sqlite-vec-database.ts)：已有 `sqlite-vec` 加载、数据库连接与向量参数适配，可作为后续复用基础。
- [主体 RAG 索引](../../packages/neuro-book/server/agent/tools/subject-rag-index.ts)与[工具](../../packages/neuro-book/server/agent/tools/subject-memory-tools.ts)：已有切块、内容哈希与向量检索链路，但来源限定为主体的 `events` 和 `memory`，不能直接搜索 note 素材。
- [Embedding 配置](../../packages/neuro-book/shared/dto/config.dto.ts)：已有独立嵌入服务配置。文本生成模型的配置不能替代 Embedding 模型配置。
- [工作区目标解析](../../packages/neuro-book/server/workspace-files/novel-workspace.ts)区分项目工作区、用户资产与工作区根；[运行数据边界](../modules/monorepo-boundaries.md#运行时路径与源码资产)已有应用 State Root。共享素材的具体归属与路径仍需设计。

SQL 不会自动绕过隔离。项目间共享需要应用层明确管理共享数据与访问接口；如果部署还使用操作系统容器，数据库连接仍受挂载、文件权限和网络可达性约束。

## 建议方案

### 用户级共享内容与派生索引

建议把正式共享素材放在应用用户数据空间，由独立素材服务管理，采用“Markdown 正文为事实来源、SQLite 为可重建检索索引”的形式。下面仅是布局示意，不是已确定路径：

```text
应用用户数据根目录/
├── shared-materials/
│   ├── 写作手法/
│   ├── 写作素材/
│   ├── 写作手法索引.md
│   ├── 写作素材索引.md
│   └── materials.sqlite
└── workspace/
    ├── 小说项目 A/
    └── 小说项目 B/
```

共享条目必须有独立保存的正文。仅把向量和另一项目的文件路径写入共享数据库，会使 AI 读取仍受项目路径权限限制，也会在来源项目删除后产生失效引用。

共享条目建议拥有稳定 ID；索引保存类别、标题、摘要、检索词、适用场景、内容位置、来源作品与项目、来源哈希、块号和 P 范围，以及内容哈希、Embedding 模型与维度。来源 P 范围用于溯源，不保证来源文件删除后仍能展开原文；若需要原文留存，必须另行决定保存方式。

### 检索与正文读取

建议新增共享素材检索与按素材 ID 读取正文的 AI 工具，由应用服务解析真实存储位置，保持普通项目文件工具原有访问边界。示意工具名称不构成最终接口。

```text
正式共享素材 → 检索信息提取 → Embedding → SQLite 索引
当前写作需求 → 分类过滤与语义检索 → 少量摘要及素材 ID → 按需读取正文
```

首期优先向量化标题、摘要、检索词、适用场景和实施要点。避免默认把很长的原作参考片段与技法说明合成一个向量，以免原作情节特征压过可迁移手法；长正文的块级索引可以后续评估。

建议结合向量检索、SQL 分类过滤与关键词检索。例如“让读者知道危险、主角暂时不知情”可以召回标题为“信息差悬念”的条目；专有名称则由关键词检索补充。候选数量应可配置并根据使用效果确定。

两份 Markdown 索引继续供人阅读及 AI 浏览；向量检索提供按需召回，不要求取消文件索引。复用 SQLite 适配器与嵌入服务能力，另建素材领域的索引和工具，不把素材塞入主体记忆或 World Engine 的领域表。

### 生命周期与失败处理

建议后续设计采用以下原则，具体状态和事务边界尚待确认：

- 仅索引已经正式保存的共享条目，提取草稿按原任务管理。
- 正文变更后依据内容哈希更新索引；删除共享条目时移除对应索引。
- 删除来源项目或提取任务时，不连带删除已正式保存的共享素材；来源失效应可识别。
- Embedding 不可用时允许保存正文，报告索引待更新并提供补建；模型或维度变化后重建对应向量。
- 多项目同时写入共享库时，由共享素材服务处理并发、重试与去重，不能仅依赖单项目 mutation gate。

## 备选方案与取舍

| 方案 | 收益 | 代价与限制 |
| --- | --- | --- |
| 共享 Markdown 正文与 SQLite 派生索引 | 沿用文件编辑、查看与备份能力；索引可以重建 | 需要维护文件与索引的同步关系，建议优先评估 |
| 正文与向量都以 SQLite 为事实来源 | 统一存储和事务管理，按 ID 读取不依赖文件路径 | 编辑、导出、备份及 Markdown 索引都需围绕数据库重新设计 |
| 保持项目正文，仅集中记录向量与路径 | 重复存储较少 | 跨项目读取权限、项目删除和移动都会影响素材可用性，需要额外合同 |
| 仅使用共享 Markdown 索引与关键词搜索 | 无需 Embedding 配置或服务调用 | 含义相近但用词不同的写作需求容易漏召回，可作为较小范围的起步方案 |

若未来各小说运行在独立操作系统容器内，可由公共服务持有 SQLite 并通过 API 提供访问。无需为本次设想提前引入外部向量数据库。

## 数据、接口、安全、迁移、发布与回滚影响

- **数据归属**：共享库属于用户数据空间，来源项目属于溯源信息；共享素材的删除、导出和备份需独立定义。
- **接口**：新增共享素材查询与正文读取接口，返回稳定身份、摘要、来源和索引状态；不开放任意 SQL 或任意跨项目文件读取。
- **访问边界**：共享范围限同一授权用户数据空间，复用现有身份与工具授权机制，不因跨项目共享而推导跨用户开放。
- **迁移**：历史项目内文件是否复制、移动或继续本地保留，尚未决定。迁移需处理重复条目、同名内容、来源链接及已保存索引，不能自动采用破坏性搬移。
- **发布与回滚**：共享库需要独立版本和备份策略。优先保证索引可重建，停用语义检索后仍能访问正文；正式内容迁移与回滚需另行制定。

## 未决问题

1. 提取确认写入时默认进入共享库、项目库，还是由用户选择？是否保留项目内副本或引用？
2. 共享库是否只包含两类 note 素材，还是以后也允许角色、势力、物品等设定进入？不同类别的复用边界如何表达？
3. 同名或相似素材采用内容哈希去重、保留独立版本，还是由用户确认合并？多来源如何记录？
4. 历史素材怎样导入；原作删除后是否需要保留引用片段或来源快照？
5. 检索元数据怎样生成，首期是否需要正文分块索引；嵌入模型、调用预算和效果验收样本怎样选择？
6. 无 Embedding、索引未完成或检索失败时，是否采用关键词检索与 Markdown 索引作为替代路径？
7. 共享素材管理入口、编辑权限、备份导出，以及项目导出时携带共享素材的范围如何确定？
