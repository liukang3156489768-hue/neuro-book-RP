# 大纲规划模块

状态：accepted

> 本提案记录开发者已确认的大纲规划模块产品方向，作为实施合同和后续 Spec 的来源。它批准进入合同与开发规划阶段，但不宣称功能已经实现；实现仍须满足 `docs/specs/outline/` 中的行为规范和验证门禁。

## 问题

NeuroBook 面向长篇小说创作，但当前缺少围绕“大纲、细纲、伏笔和情节线路”进行集中规划、追踪和回收的模块。大纲内容只能以普通资料或分散笔记承载，难以形成从宏观规划到章节执行、从伏笔埋入到回收验证的闭环，也无法让 Agent 稳定地读取规划上下文并在写作过程中协助维护。

## 目标与非目标

### 目标

1. 为作品提供独立的大纲规划空间，支持从宏观结构逐步下钻到细纲和可执行的情节节点。
2. 将伏笔作为可追踪对象管理，而不是只存在于正文或自由文本中。
3. 支持多条故事线路的规划、交叉、切换和进度观察。
4. 记录伏笔的埋入、发展、回收或失效过程，能够发现遗漏、冲突和超期未回收项。
5. 让 Agent 在用户授权范围内协助生成、补全、检查、关联和维护规划数据，同时保留用户审阅与确认边界。
6. 使大纲规划能够服务后续写作、章节推进、连续性检查和复盘，而不是成为孤立的文档编辑器。

### 非目标

- 本阶段不直接替代正文编辑器或章节写作器。
- 不自动决定作品的唯一正确结构，也不把模型推断直接当作作品事实。
- 不在没有用户确认或自动模式明确授权的情况下改写正式规划；任何模式均不得因此越权改写正文，删除仍须单独审核。
- 不将全部历史聊天、全部正文或全部素材无条件注入模型上下文。
- 在数据合同尚未明确前，不强行把已有自由文本一次性迁移为完整结构化实体。

## 当前行为与证据

本次先记录开发者提出的产品缺口和初始架构，尚未对现有代码、数据模型和写作流程做专项核验。因此，以下判断属于需求基线，不宣称已经完成实现级调查：

- 当前项目已有长篇小说写作能力，但缺少一个围绕大纲、细纲、伏笔和线路的统一规划与使用模块。
- 开发者明确提出初始架构为“大纲库 + 伏笔库 + 线路规划 + 伏笔埋入与回收管理 + Agent 协助”。
- 后续设计需要核对现有作品数据、章节/正文存储、Agent 上下文装配、历史记录和现有素材模块，避免新增平行所有权。

## 方案、备选方案和取舍

### 与《新小说编写计划》的替换关系

[《新小说编写计划》](../../新小说编写计划.md)是开发者的原始设计文档，其中的 Agent 和模块均未开发。本提案只替换其中的大纲与细纲部分和伏笔部分；原文件按原文保留，其余部分仍按原始设计开发。它是开发设计文档，不是用户作品数据，不作为产品迁移的来源。

| 原始设计 | 处理 |
| --- | --- |
| 大纲库、故事线可视化、伏笔模块；伏笔三状态与章节计数；规划 Agent 权限表 | 由本模块的大纲库、线路规划、伏笔库、四状态派生和讨论／自动模式替换 |
| `outline`、`Detailed outline`、`foreshadowing` 三个 Agent | 作为本模块主 Agent 的专用子 Agent 保留，见“模块 Agent 的专用子 Agent” |
| 正文写作 Agent `writer.pro`、正文交付与作品级人称、文风输入 | 仍按原始设计开发；`writer.pro` 是新 Agent，不改造现有 `writer` Profile；其细纲、写作指导、参考文件和篇幅输入改为读取本模块的固定线路交接 |
| `lorebook/` 八类素材目录与按需读取 | 本模块 Agent、子 Agent 与 `writer.pro` 共用 |

原始设计与本提案冲突时，被替换部分以本提案为准；其余部分以原始设计为准。

从原始设计吸收并归并到本模块的内容包括（2026-09-26 补充的细化内容见“原始设计补充”一节）：

- 原 `outline` 的故事骨架、卷级／章级大纲、伏笔安排和标记职责，归入大纲库与模块 Agent 协助；
- 原 `Detailed outline` 的章节承接、场景顺序、人物行动、对白意图、信息披露、写作指导、参考文件和篇幅控制，归入章节大纲下的细纲；
- 原 `foreshadowing` 的伏笔名称与编号、伏笔内容、埋设建议和回收建议，归入伏笔库的设计产物；
- 原故事线可视化的“已确认条目进入线路、节点引用原大纲条目而不复制正文、同一条目可被多条线路引用”等约束，归入线路规划；
- 原规划 Agent 的素材按需读取和用户授权边界，归入本模块 Agent 与 `lorebook/` 关联规则。

新模块是大纲、细纲、伏笔和线路规划的规划所有者，并与现有 Plot 互补而不冲突：本模块不替换、复制或重建 Plot 的 Story、Thread、Scene、Promise、Decision、World Engine 关联和 Writer Brief；跨模块只通过稳定 ID、版本和明确的只读交接或适配器协作。被替换部分出现重叠或冲突时，以本 Proposal、关联 ADR 和 `docs/specs/outline/` 下的 planned Spec 为准；本 Proposal 已被接受为实施基线。

### 初始方案：结构化规划库与 Agent 协作闭环

采用五个相互关联的能力面：

1. 大纲库：承载总纲、卷纲或篇章纲、细纲和情节节点。
2. 伏笔库：承载伏笔实体、生命周期、埋入/强化/回收计划及来源标记。
3. 线路规划：承载主线、支线、人物线、感情线、谜团线、势力线和 IF 线等叙事线路。
4. 伏笔埋入与回收管理：解析正式大纲条目中的伏笔标记，形成埋设和回收的规划检查闭环。
5. Agent 协助：负责提议、整理、检查、解析标记来源和生成上下文；用户或既有授权策略负责确认正式变更。

采用该方案的原因是：它同时覆盖灵感整理、线路编排、规划检查和写作协助，能把“想写什么”“最终如何编排”和“还缺什么”连接起来。大纲库负责承载可供选择的想法，线路规划负责确定剧情顺序和正文使用范围。

### 规范来源、文件布局与领域边界（已确认）

- 结构化项目文件是大纲规划模块的唯一规范来源；SQLite 只保存可重建索引、查询加速数据和解析摘要，不拥有规划正文、关系、线路顺序或伏笔事实的最终决定权。
- 规划文件采用可审阅的 YAML + Markdown 组合：
  - `outline/manifest.yaml` 保存模块版本、当前规划版本和顶层索引；
  - `outline/entries/<slug>--<stable-id>.md` 保存总纲、卷纲、章节大纲和细纲，YAML front matter 保存结构化字段，Markdown 正文保存叙述内容；
  - `outline/foreshadowing/<slug>--<stable-id>.md` 保存伏笔定义和设计说明；
  - `outline/lines/<slug>--<stable-id>.yaml` 保存节点、边、线路类型、固定状态、剧情顺序和可选 UI 坐标，业务顺序与坐标分离。
- 稳定 ID 不因移动、重排、改名或关系变化而改变；共享条目修改采用写时分叉，生成新文件、新稳定 ID 和新文件名，不覆盖源文件且不重新合并。
- 对象删除是删除规范文件；关系删除只移除父子、引用、节点关联或线路成员关系。被引用对象必须先解除活动引用并完成影响预览、确认和历史记录，禁止隐式级联删除共享对象。
- 大纲规划模块拥有灵感大纲、细纲、伏笔标记和正式线路节点；现有 Plot 继续拥有作者视角的剧情组织、Scene、Promise、Decision、World Engine 关联和 Writer Brief，首期不建立第二套 Scene 真相源。
- 《新小说编写计划》是开发设计文档，不是用户规划数据；本模块不提供从它或其他旧笔记导入规划的功能（2026-09-26 撤销此前的迁移设计）。

### 暂不采用的备选方案

- **仅做大纲文档编辑器**：实现较快，但无法稳定追踪伏笔、线路和最终编排，也难以支持 Agent 的结构化协助。
- **仅做知识图谱/关系图**：关系展示能力强，但不一定适合日常规划、顺序写作和用户快速编辑，且容易把视觉复杂度置于可执行性之前。
- **完全由 Agent 自动维护**：能够减少手工操作，但模型推断可能污染正式规划，难以解释和回滚，因此不作为默认行为。

## 初始架构

### 1. 大纲库

大纲库承载作品的结构化规划，至少需要区分：

- 故事总纲：作品核心冲突、主题、结局方向和整体阶段。
- 卷纲或篇章纲：按卷、篇章、幕或阶段拆分的中长期目标。
- 细纲：可映射到章节或场景的具体情节安排、冲突、转折、结果和写作提示。
- 情节节点：可被线路、伏笔、人物目标和章节引用的最小规划单元。

大纲库应支持层级关系、引用关系和版本/状态信息，但不要求用户在大纲库中维护严格的剧情先后顺序；大纲条目的剧情顺序、节点关系和正式使用范围由线路规划确定。

### 1.1 大纲库的创建与层级结构

大纲库支持两种创建入口：

1. **手动新建**：用户直接创建总纲、卷纲、章节大纲或其下的细纲。
2. **方向生成**：用户先提供简单的故事方向、目标或约束，由 Agent 协助生成大纲草案，生成结果进入可审阅的草稿状态，不直接视为正式采用的大纲。

大纲采用三级层级：

- **总纲**：作品整体层面的故事方向、核心冲突、主题、主要阶段和结局方向。
- **卷纲**：总纲下的阶段性规划，描述一卷或一个较大篇章的目标、冲突、推进和收束。
- **章节大纲**：卷纲下可执行到章节的剧情规划，描述该章节需要发生的主要事件、冲突、转折和结果。

章节大纲通常关联一个**细纲**，也允许将多个连贯的场景细纲绑定到同一章节大纲。细纲不是第四级大纲，而是依托章节大纲进行展开和丰富的写作指导层。原则上不允许脱离章节大纲单独存在；允许章节大纲暂时没有细纲。章节大纲与正文按一对一关系关联。

大纲库采用层级阶梯式展开：用户可以沿总纲、卷纲、章节大纲逐级展开，也可以在节点级别查看其关联细纲、伏笔、素材和线路信息。大纲库允许同时存在多个独立的作品方案，例如方案 A 和方案 B；方案 A／方案 B 表示同一部作品完全不同的展开，不是线路规划中的普通分支。全局总纲只有一个，作为所有方案的共同纲领；每条方案链通过关系引用这个总纲，并在其下组织各自的卷纲和章节大纲。线路规划中的 IF 线则用于在某一方案内部，通过树状节点图表现分支走向和不同结局的分化起点。不同方案应拥有清晰的方案标识和独立层级，不能因为展示在同一个库中就默认互相覆盖。

在每一级大纲上，用户都应能执行新增、编辑、移动、排序和删除操作。大纲库中的移动和排序主要服务于用户整理灵感与层级，不代表正式剧情先后；正式的剧情顺序、节点关系和正文使用范围由线路规划确定。全局总纲可删除但必须二次确认；方案链可以新增或删除其卷纲、章节大纲关系，不得借此复制出第二个总纲对象。跨方案复用时，初始关系仍是同一条目被多个位置引用；如果用户修改被复用条目，系统必须先弹窗确认，用户确认后才在当前修改位置建立具有全新稳定 ID 和不同文件名的独立新文件。原文件和其他引用位置不受影响；用户可以查看原条目，但不允许将分叉条目重新合并回共享条目。包括：

- 管理全局唯一总纲；
- 新增、删除或调整方案链及其卷纲关系；
- 在方案链下新增、删除或调整卷纲；
- 在卷纲下新增、删除或调整章节大纲；
- 为章节大纲新增、编辑或删除关联细纲；
- 在多条方案链之间切换、查看和管理。

总纲允许删除，但必须先展示所有级联影响并经过二次确认。已被其他位置引用的条目默认锁定、不能删除；界面应指出阻止删除的引用及处理入口，待引用全部解除后才能删除。解除引用关系与删除条目本体是不同操作，不能把前者当作后者的隐式级联。移动或重排不改变稳定 ID；删除卷纲、章节大纲、细纲或线路对象也须先预览对下级条目、伏笔标记、线路节点和正文关联的影响。任何模式下 Agent 发起的删除均须审核，不得静默级联删除。

### 1.2 章节大纲的结构化要素

章节大纲除了剧情正文外，还包含三类用于同步规划关系和提供写作上下文的结构化要素：

#### 大纲正文

大纲正文是章节大纲的剧情正文，描述本章计划发生的剧情、冲突、转折、结果和必要的写作意图。它是用户阅读和编辑章节规划的主体内容。

#### 伏笔使用标记

伏笔使用标记用于在章节大纲正文中标记本章使用了伏笔库中的哪一条或多条伏笔。用户界面以类似文档注释的下划线标注呈现，鼠标悬停时显示关联伏笔、动作类型和来源信息；系统层面使用 Markdown 结构化文本表示。其预期行为为：

- 用户在正文中插入与伏笔库条目的关联标记；
- 用户界面以类似注释的形式展示该引用，不破坏正文阅读；
- 程序解析标记并同步到伏笔库；
- 伏笔库记录对应伏笔实际埋设或使用的章节；
- 标记应能反向跳转到伏笔条目和章节大纲位置。

#### 伏笔回收标记

伏笔回收标记与伏笔使用标记采用同类机制，用于标记本章回收哪一条伏笔以及具体回收位置。解析后应同步到伏笔库，记录伏笔的回收章节和对应位置，并允许用户查看回收标记的来源。一个章节通常不同时承担同一伏笔的埋设和回收，但允许用户明确这样规划；程序必须禁止没有有效埋设记录就先产生有效回收记录。

使用标记与回收标记在用户界面上可以采用相近的注释形式，但在结构化数据中必须区分操作语义，避免把“本章使用了伏笔”和“本章完成了伏笔回收”混为同一事件。

#### 使用素材索引

使用素材索引用于标注本章节大纲引用或依赖的素材文件，包括但不限于：

- 角色资料；
- 世界观资料；
- 物品资料；
- 特殊规则资料；
- 其他属于 `lorebook/` 的项目素材。

素材索引应使用可稳定解析的文件或素材标识，而不是只保存显示名称，便于 Agent 在生成细纲、写作前准备和一致性检查时准确读取来源。

### 1.3 细纲设计

细纲依托章节大纲生成，主要用于对章节大纲进行细化和文本丰富。细纲可以由用户手动编写，也可以由 Agent 根据所属章节大纲生成草案；生成后的细纲仍需与所属章节大纲保持明确关联。细纲保存时需要先由用户选择“草稿”或“正式文本”：草稿不触发 AI 分析，也不进入正式写作使用范围；正式文本保存前必须运行与章节大纲的 AI 偏差和冲突分析并展示结果。默认处理：发现偏差不悄悄改写细纲；讨论模式向用户展示证据，可修订重试或确认带警告保存；自动模式在完成分析后可带警告保存并记录可撤销结果，不再要求逐次确认。分析未完成或失败不能当作通过正式校验，两种模式均不可跳过分析。

细纲包含以下标注要素：

- **素材使用索引**：与章节大纲的素材索引保持一致，用于告知本篇细纲编写涉及哪些角色、世界观、物品、特殊规则等文件。细纲默认继承所属章节大纲的索引，并可局部调整，优先级为：排除 > 覆盖 > 追加 > 继承。
  - 继承：未声明的类别沿用章节大纲索引；
  - 追加：细纲自己声明的条目与继承结果取并集，按稳定标识去重；
  - 排除：显式移除某个继承条目，被排除的条目不再出现在细纲生效索引中，即使它同时被追加；
  - 覆盖：细纲声明了该类别时，用细纲的条目替换章节大纲在该类别的全部条目。
  生效索引以细纲声明为准计算，解析失败或引用不存在时按异常处理，不静默回退到继承结果。
- **写作指导标注**：用于告诉写作 Agent 此处应采用的描写手法、叙事视角、情绪强度、节奏、语言风格或其他写作约束。用户界面通常以注释形式呈现，文件层面使用结构化文本标注，以便机器可靠读取。
- **参考文件标注**：用于告知写作 Agent 在编写此处内容前需要先阅读哪些资料。它与素材使用索引的区别是：素材索引表达本篇涉及哪些素材，参考文件标注表达生成当前片段前必须或建议先阅读哪些内容。
- **篇幅要求**：用于控制章节或细纲片段的目标字数、范围或分配，防止内容失控和无效扩写。具体采用目标值、上下限、区间还是各细纲片段分配，需要在后续合同中确定。

### 1.4 大纲条目标记

大纲库条目使用以下标签进行区分：

- **草稿**：尚未正式采用、仍处于编辑或审阅中的规划。
- **正式采用**：已经确认并作为当前规划依据的大纲条目。
- **埋设伏笔**：该条目包含或承担伏笔埋设动作。
- **回收伏笔**：该条目包含或承担伏笔回收动作。

这些标签分为两个维度：`草稿／正式采用`属于采用状态；`埋设伏笔／回收伏笔`属于可叠加的行为标签。一个章节大纲可以同时为正式采用、埋设伏笔和回收伏笔。实现时不得用单一互斥枚举字段丢失这种组合关系。
### 2. 伏笔库

伏笔库承载可追踪的伏笔实体及其生命周期。每条伏笔至少应能表达：

- 伏笔意图与读者预期效果。
- 首次埋入位置、后续强化位置和计划回收位置。
- 关联人物、地点、道具、事件、线路和大纲节点。
- 状态严格依据本提案 2.1 节定义的“草稿、待使用、已埋设、已回收”四种状态；标记损坏、引用失效和顺序错误作为异常信息记录，不新增其他生命周期状态。
- 回收条件、允许延迟范围、风险等级和备注。

伏笔库应支持从规划反查正文，也支持从章节或正文发现尚未登记的潜在伏笔，但“发现”不应自动等同于“确认入库”。

### 2.1 伏笔库的用途与条目状态

伏笔库用于存放已经设计的伏笔，并持续记录每条伏笔在大纲规划中的埋设与回收情况。它既是伏笔设计的存储空间，也是大纲库标记解析结果的汇总和追踪入口。

伏笔库条目采用以下四种状态：

- **草稿**：伏笔尚在设计、编辑或审阅中，尚未作为可正式引用的伏笔投入使用。
- **待使用**：伏笔已被确认存入伏笔库，但程序尚未在大纲库中解析到该伏笔的有效埋设标记。
- **已埋设**：程序已在大纲库中解析到该伏笔的有效埋设标记，但尚未解析到对应的有效回收标记。
- **已回收**：程序已在大纲库中解析到该伏笔的有效回收标记。

状态的核心依据是大纲库中的结构化伏笔标记，而不是 Agent 的单次判断或用户在伏笔条目上手动填写的孤立状态。状态计算至少需要检查该伏笔是否存在有效埋设标记和有效回收标记：

| 埋设标记 | 回收标记 | 计算状态 |
|---|---|---|
| 无 | 无 | 待使用 |
| 有 | 无 | 已埋设 |
| 有 | 有 | 已回收 |

伏笔状态不按方案 A、方案 B 或其他大纲链分别拆分显示，而是汇总全部有效正式大纲标记计算。伏笔条目仍需保留每个埋设、强化和回收标记的来源位置，因此用户可以反查具体由哪一个大纲条目和线路节点产生了记录；来源可追溯不等于状态需要按方案分栏。伏笔状态只从正式大纲条目中的埋设和回收标记获取与确认，不以正文内容或正文解析结果作为状态依据。

“草稿”是进入上述计算状态前的设计生命周期状态。后续需要明确草稿是否参与标记解析、是否允许被大纲引用，以及草稿被用户确认后如何转为可使用条目。若发现只有回收标记而没有埋设标记，或标记引用目标不存在、格式无效、来源已失效，系统不应静默判定为已回收，而应报告为异常并保留待处理状态。

伏笔条目还应保留可追溯记录，包括：

- 伏笔的设计内容、预期效果和回收意图；
- 关联的大纲链、总纲、卷纲、章节大纲和细纲；
- 已解析的埋设标记与回收标记来源位置；
- 标记解析时间、来源版本或正文哈希；
- Agent 提议、用户确认和状态变化记录。

### 2.2 伏笔设计与存储

伏笔库提供独立的伏笔设计能力。用户可以提供一个灵感、一个片段、一个悬念方向或其他自然语言描述，由 Agent 协助整理和生成伏笔方案，并将结果保存到伏笔库。

伏笔设计流程建议区分以下阶段：

1. 用户提供灵感或设计目标。
2. Agent 生成一个或多个伏笔候选，包括伏笔内容、预期埋设方式、可能回收方向和适用线路。
3. 讨论模式由用户审阅、编辑、选择或驳回候选；自动模式可在授权范围内直接采用非删除操作，但需保留可撤销的变更记录。
4. 经讨论模式确认或自动模式授权采用后，候选才保存为正式的伏笔库条目；未采用内容保留为草稿或建议，不得直接参与正式状态计算。

伏笔设计结果可以关联 `lorebook/` 中的角色、世界观、物品、特殊规则等素材，但素材引用应保持可定位，不能只保存模型生成的名称。

### 2.3 伏笔在大纲编写中的使用

在编写大纲时，伏笔可以通过两种方式进入章节大纲：

- **用户主动使用**：用户明确选择伏笔库条目，并在章节大纲中插入伏笔使用标记或伏笔回收标记。
- **Agent 提议使用**：Agent 根据当前大纲内容、线路、素材和已有伏笔提出引用建议，或在生成大纲/细纲时引用某条伏笔。

Agent 引用伏笔的场景按当前模式处理：讨论模式必须经用户审批，才能转化为正式采用的伏笔使用或回收关系；自动模式已经获得用户对非删除操作的持续授权，可直接采用并更新规划状态，不再逐条审批。未获得对应模式授权的建议只能作为草稿或待确认变更，不得改变正式伏笔状态；两种模式都不能绕过有效埋设先于回收等结构约束。

用户审批应能看到至少以下信息：

- Agent 建议使用的伏笔条目；
- 建议插入的大纲链、卷纲、章节大纲或细纲位置；
- 建议属于埋设还是回收；
- 建议引用的文本范围或标记位置；
- 该操作可能造成的状态变化及影响对象。

讨论模式审批通过或自动模式在授权范围内采用后，程序写入正式结构化标记并重新计算伏笔状态；审批拒绝或撤销时，不应留下会被解析器误认为正式事实的残留标记。

### 3. 线路规划

线路规划承载主线、支线、人物线、感情线、谜团线、势力线和 IF 线等不同叙事线路。线路应能关联大纲节点、章节、人物、伏笔和关键事件，并展示：

- 线路目标、起点、阶段和预期终点。
- 线路之间的依赖、交汇、冲突和优先级。
- 当前推进状态与最近一次推进位置。
- 长时间未推进、与其他线路冲突或偏离总体规划的风险。

线路规划不应只是一组标签；它需要支持沿时间或章节顺序观察线路如何推进、交叉和收束。

### 3.1 线路规划界面与文件表达

线路规划界面采用节点图形式呈现：节点代表线路中的情节或规划单元，连线代表节点之间的先后或推进关系。用户可以在界面中新增和删除节点，并通过连线建立节点之间的关联。

在文件层面，线路规划保存为 `outline/lines/<slug>--<stable-id>.yaml`，其中节点、边、线路类型、固定状态和剧情顺序是业务事实，可选 UI 坐标仅是布局数据。结构化文件是规范来源；SQLite 仅承担可重建的索引、查询和运行期缓存，不成为与文件并列的可写真相。结构化文本至少应能表达：

- 节点的稳定标识、标题和说明；
- 节点之间的连线关系；
- 节点的左右顺序或时间顺序；
- 节点关联的大纲库条目；
- 节点链的类型和所包含节点；
- 程序解析出的重复节点和冲突分析结果。

界面图形是结构化线路数据的可视化投影，不能成为唯一数据源。用户在图形界面中的有效新增、删除、连线和排序操作应先校验、再写文件，随后刷新索引；不得让数据库先成为不可追溯的正式事实。重新打开模块或文件被外部修改时应重新解析文件并恢复节点图或给出可定位错误；写入时检测文件版本变化，不静默覆盖外部更改，冲突需展示差异并由用户选择。解析失败应保留原文与上次有效投影，不将损坏内容静默同步成删除；系统可以在 Agent 界面中请求 Agent 分析损坏标记并提出修复方案，修复仍遵循当前用户确认和 Agent 权限规则。

### 3.2 节点与大纲条目关联

用户新增节点后，点击节点可以展开关联列表。该列表内容来自大纲库中的条目，用户可以为当前线路节点选择关联的大纲条目。

关联对象原则上包括总纲、卷纲、章节大纲和细纲等大纲库条目。一个线路节点只表示并关联一个大纲库条目，也可以先建为空节点再关联；同一方案的线路图中，一个大纲条目最多对应一个节点，这个节点可以被多条线路共享，用来表达分叉和汇合。节点不是大纲条目的副本，关联通过稳定标识保存。在线路规划中经用户或获得授权的 Agent 确认并固定的节点，才构成正式线路；其中关联的章节大纲才是正式用于正文编写的章节大纲，未固定的节点只是候选编排内容。

大纲条目关联应保留稳定标识，而不是只保存标题。用户点击关联项时，应能在大纲库中定位原条目；大纲条目被移动、重命名或删除后，线路规划需要能够识别关联失效并向用户提示。

### 3.3 节点链类型与设置流程

每个方案有一张共享的线路图，节点和连线本身不带线路类型。线路是在图上勾选节点组成的链：按格号排序后格号严格递增、相邻节点之间有连线、至少 2 个节点。分叉与汇合通过多条线路共享节点表达，单条线路内部不分叉。

设置节点链性质时，流程为：

1. 用户选择需要设置的节点链类型；
2. 从节点图中逐个勾选属于该节点链的节点；
3. 程序校验所选节点之间是否形成有效的链式关系；
4. 保存节点链类型及其包含的节点。

节点链类型包括：

- **主线**：当前正式规划版本的核心叙事链；每个正式规划版本最多允许一条节点链被设置为主线，每个节点至多拥有一条主线方向的连接；草稿版本可以暂时没有主线；切换主线时保留原节点链，但取消其主线属性；
- **支线**：从主线分出、与主线并行或对主线形成补充的叙事链；
- **角色线**：围绕某个角色或角色群展开的叙事链；
- **IF 线**：从主线分化出的另一种可能走向，约束与主线相同，每个节点至多拥有一条 IF 线方向的连接。

其他支链或独立节点链只能设置为支线、角色线或 IF 线，不能再设置为主线。一个节点可以同时成为主线、支线、角色线和 IF 线等多种线路的起点，也允许被多个节点同时连接。主线属性采用单一设置入口：同一正式规划版本内设置新主线时替换旧主线归属，旧节点链保留但不再是主线；界面与数据约束均不能创建第二条主线，无须把“两条主线冲突”交给 AI 检查。

“节点链”与“线路类型”需要在数据层分开表达：节点链是节点的有序集合及其连接关系，线路类型是对该集合的业务分类。这样可以支持同一组节点被不同视角引用，同时避免通过修改标签破坏图结构。

### 3.4 节点顺序与图形布局

线路图横向分格，最左为格 0、最右为格 n，格号就是方案内的全局剧情先后，程序读取节点所在格号即可确认剧情顺序：

- 越靠左的节点越接近故事开局；
- 越靠右的节点越接近故事结尾；
- 同一格可以放多个节点，表示并行剧情；
- 纵向也分行，拖动节点时吸附到“格×行”，行号只是排版，没有剧情含义。

连线只能从小格号指向大格号，可以跨格，同格节点之间不能连线。插入列会把格号 ≥ c 的节点整体右移一格，不改变相对顺序。一个节点允许拥有多个入边，关键转折节点可以同时被多个节点连接，并可以成为多种线路类型的起点。线路图虽然以树状图呈现，但由于允许多入边，数据模型实际按带类型的有向无环图处理；回忆、倒叙作为节点内容表达，不通过逆向连线破坏剧情顺序。设置节点链时要求勾选节点按格号连续相连，允许多线交汇和共用节点；连线向右的约束保证不能通过环回到过去。

### 3.5 线路冲突分析与重复节点解析

线路规划提供 AI 辅助分析能力，用于检查节点链是否出现剧情上的冲突问题，例如：

- 节点先后关系与大纲内容不一致；
- 同一角色、事件或关键事实在不同节点中的描述互相矛盾；
- 节点链之间存在时间、因果或人物状态冲突；
- 某条线路偏离主线或与其他线路形成无法解释的重复推进；
- 节点缺少必要的前置事件、承接关系或收束节点。

AI 分析结果属于检查建议，不直接修改节点链或大纲条目。结果应区分已确认事实、模型推断和待用户处理的问题，并能定位到具体节点、大纲条目或关联关系。程序负责确定性的引用失效、重复标识、断链、逆序和成环检查；AI 负责因果、人物状态等剧情语义冲突，不承担第二条主线检查。分析记录绑定输入版本；关联的大纲条目修改后旧结论失效，节点保持黄色，直到当前版本重新完成 AI 冲突分析。冲突发现后的处理由用户决定，也可以委托获得授权的 Agent 执行；无论由谁处理，都必须遵守当前权限模式并保留变更记录和撤销能力。

重复节点由程序解析和标注，而不是只交给 AI 判断。程序应根据节点稳定标识、关联的大纲条目标识和必要的结构化特征识别重复，并在图形界面与结构化文本中保留重复标注。重复节点不能用于剧情编写，也不能被固定为正式线路；用户必须处理重复关系，并在处理后重新完成冲突分析，节点及其所属线路通过检查后才能继续使用。用户可以查看重复来源、确认处理范围，或拆分、合并和解除关联；具体操作不得静默删除原对象。若外部文件编辑或旧数据导致引用目标已不存在，节点仍标记为红色并必须重新关联有效条目后才能继续使用；若关联条目被修改，节点标记为黄色，并必须重新经过 AI 冲突分析后才能作为已确认节点使用。
### 4. 伏笔埋入与回收管理

该部分负责解析正式大纲条目中的伏笔标记，形成可检查的规划闭环：

- 记录每次埋设、强化和回收标记及其来源大纲条目。
- 依据有效的正式埋设和回收标记动态计算伏笔库状态。
- 提醒尚未埋设、已经埋设但尚未回收、回收顺序异常或标记引用失效的伏笔。
- 允许用户或获得授权的 Agent 通过正式大纲条目修正标记。

伏笔的“已埋设”和“已回收”只以正式大纲条目中的有效标记为依据，不读取正文、不依赖正文证据，也不将正文解析结果写入伏笔状态。

### 5. Agent 协助

Agent 作为规划助手，而不是拥有模块外写入权的自动编剧。初始可考虑以下能力：

- 根据作品目标和已有规划生成大纲草案、细纲草案或线路草案。
- 将自然语言规划整理为结构化节点、关系和伏笔候选。
- 对大纲进行完整性、节奏、冲突、因果和线路覆盖检查。
- 在写作前提供本章相关的线路、伏笔、人物目标和限制条件。
- 根据正式大纲条目检查线路、伏笔标记和章节规划的一致性。
- 对规划变更影响进行预览，例如修改某个节点会影响哪些章节、线路和伏笔。

Agent 输出应区分“事实/已确认数据”“模型推断”“待用户确认建议”。讨论模式逐项或按批次确认后写入；自动模式对模块内非删除操作采用持续授权，无须逐项审批，但须可见、可追溯、可撤销；任何删除仍需用户审核。

## 布局与交互骨架

### 总体布局

大纲规划模块采用全屏左右分栏布局。左侧 Agent 区域固定贯穿窗口顶部到底部，右侧为当前规划视图工作区；默认按窗口宽度划分为左侧约 `1/5`、右侧约 `4/5`，具体像素宽度随窗口尺寸变化，不把比例写死为固定像素。左右栏之间提供可拖拽的分隔线，用户可以在运行时调整两侧宽度；调整后的比例属于界面布局状态，不改变模块数据和权限边界。当前阶段不做小屏、窄屏或移动端适配，窗口尺寸不足时不承诺自动折叠、抽屉化或其他响应式降级行为。

```text
┌──────────────────────┬──────────────────────────────────────────────┐
│                      │             大纲库 | 伏笔库 | 线路规划       │
│                      │──────────────────────────────────────────────│
│    Agent 对话区       │                                              │
│    宽度约 1/5         │                 当前视图工作区               │
│    高度贯穿全屏       │                                              │
│                      │                                              │
│  思考｜模型｜温度     │                                              │
│  讨论 / 自动模式      │                                              │
└──────────────────────┴──────────────────────────────────────────────┘
```

- **左侧**为常驻性质的 Agent 聊天界面，呈纵向长方形，从窗口顶部延伸到底部。它在用户切换大纲库、伏笔库和线路规划时保持存在，不因右侧界面切换而销毁会话或丢失上下文。
- 左侧聊天区底部包含消息输入框；输入框下方提供四类控制项：思考开关、模型选择、温度设置、讨论模式／自动模式切换。思考开关使用两段式按钮在开启与关闭之间切换；模型设置使用列表选择模型；温度设置使用数值框配合增加／减少调整按钮，不使用滑块控件；讨论模式／自动模式继续使用模式切换控件。上述控制项作用于后续 Agent 请求，不改变已经生成或已经执行的历史结果。
- Agent 对话中的上下文列表支持以流式方式呈现 AI 输出内容：生成中的内容应按到达顺序逐步显示，而不是等待整段响应完成后一次性出现；流式输出结束、被取消或失败时需要呈现对应结果状态。流式展示只影响显示过程，不改变审批、正式写入和撤销规则。
- **右侧**约占窗口宽度的 `4/5`，是规划工作区。顶部居中放置三段式切换按钮，三个选项依次为“大纲库”“伏笔库”“线路规划”；下方主体区域展示当前选中视图的内容。
- 右侧视图切换不改变全屏布局，也不移除左侧 Agent；当前作品、当前规划版本和当前选择上下文在左右区域之间共享，但各视图拥有清晰的显示与数据职责。
- `1/5` 与 `4/5` 是默认布局比例，左右栏支持通过分隔线拖拽调整；左侧 Agent 区域的宽度最大不得超过窗口中线，即不超过 `1/2`。当前阶段不做小屏、窄屏和移动端适配。布局状态需要按当前项目持久化，用户重新进入项目、重新打开项目或重载 UI 后均应恢复上次保存的左右栏比例；最小可用宽度和保存触发时机仍待后续 UI 合同细化。

### 模块 Agent 的权限与职责

该 Agent 是大纲规划模块的专属协作入口，默认拥有：

- 对当前项目目录 `lorebook/` 的读取权限，用于理解项目已有设定、素材、章节规划和相关上下文。
- 对整个大纲规划模块的读取权限，用于查询大纲节点、伏笔、线路、关联关系、状态、标记来源和历史变更。
- 对整个大纲规划模块的写入与操作权限，用于创建、修改、关联、整理、检查、生成建议和执行模块内的规划动作。伏笔状态只能通过增删改正式标记间接改变，不存在直接写状态的操作。

上述权限应限定在产品定义的模块边界内：Agent 可以操作大纲规划模块的数据和动作，但不应因为拥有模块权限而自动获得任意正文文件写入、项目目录删除、其他模块数据修改或越权执行宿主系统操作的能力。模块提供“讨论模式”和“自动模式”：讨论模式下，Agent 先展示提案或变更摘要，由用户逐项或一次确认一批后写入；自动模式下，非删除操作可直接执行并展示结果，删除对象或解除引用等删除行为仍须审核，总纲删除还需二级确认。两种模式都应对级联影响先做预览，批量操作一次确认整个明确列出的范围即可，不要求逐条重复审批，并提供针对已执行变更的撤销按钮及可追溯记录。

Agent 的主要任务是协助用户使用大纲规划模块，包括：

- 解释当前界面和规划对象的用途。
- 根据用户要求创建或调整大纲、伏笔和线路规划。
- 在模块内查询关联对象并执行整理、检查和关联；伏笔状态随正式标记的变更重新派生。
- 结合 `lorebook/` 的只读内容，为当前规划提供背景和一致性参考。
- 根据右侧当前页面、选中对象和用户会话，提供上下文相关的建议，而不是每次都要求用户重复说明目标。

Agent 的操作结果需要区分“已执行”“已生成草稿”“待用户确认”和“执行失败”。撤销按钮须以本次操作或批次为单位恢复文件及派生索引和状态；遇到后续修改或外部文件冲突时不可静默覆盖，应提示用户处理。切换自动模式与讨论模式只改变后续操作的审批行为，不追溯批准已有建议。

两种模式都以用户当前指令为操作范围。例如用户要求“把这一卷拆成十章并创建对应条目”后，Agent 可在该范围内连续新增和修改；超出范围的改动需先说明，再按当前模式另行确认，自动模式也不例外。

### 模块 Agent 的专用子 Agent

原始设计中的 `outline`、`Detailed outline`、`foreshadowing` 三个 Agent 作为模块主 Agent 的专用子 Agent 实装，处理各自领域的专业问题：

| 子 Agent | 负责的问题 |
| --- | --- |
| `outline`（大纲） | 总纲、卷纲、章节大纲的骨架与方案组织；安排已有伏笔的埋设、强化与回收 |
| `Detailed outline`（细纲） | 依托章节大纲编写细纲、写作指导、参考文件和篇幅 |
| `foreshadowing`（伏笔） | 伏笔设计，以及结合派生状态给出埋设与回收建议 |

- 主 Agent 是用户唯一的对话与审批入口。它判断问题是否需要专业处理，委派给对应子 Agent，再核对子 Agent 的结果并向用户说明。简单查询由主 Agent 自己处理。
- 子 Agent 是最终条目的产出者，对规划模块和 `lorebook/` 有读写权限。主 Agent 以两种方式使用它们：
  - **咨询**：子 Agent 只读取和预览，结果作为建议交回主 Agent，由主 Agent 按模式经用户确认后执行；
  - **委派产出**：子 Agent 在主 Agent 给定的任务范围内直接写入规划条目和 `lorebook/` 素材。讨论模式下，用户先确认这次委派及其范围，委派期间的写入无须再逐条确认；自动模式直接执行。
- 子 Agent 的写入只在一次经放行的委派期间有效，由服务端校验：
  - 规划写入仍经过规划领域服务的预览、版本与结构校验；
  - `lorebook/` 写入只限当前 Project 下 `lorebook/` 内的 Markdown 文件，不能写正文、`outline/` 规范文件或其他目录；
  - 子 Agent 不能删除对象、解除关系或操作线路，这类操作交回主 Agent，删除始终审核；
  - 子 Agent 不能撤销或调用其他 Agent。
- 主 Agent 向用户逐项汇报子 Agent 的写入结果；规划写入可按事务撤销。
- 子 Agent 不直接向用户提问；需要澄清的问题随结果交回主 Agent。
- 子 Agent 会话挂在主 Agent 会话之下，绑定同一 Project，并沿用主 Agent 当前的模型选择；同一主会话内同类子 Agent 复用同一会话，以保留专业上下文。
- 只有模块主 Agent 能委派这三个子 Agent。模块主 Agent 不获得通用的创建 Agent 能力，不能借委派创建正文写作或其他模块的 Agent。

### 三段式界面切换

右侧顶部的三段式按钮是大纲规划模块的一级导航，而不是一次性过滤器：

- 选择“大纲库”时，右侧进入总纲、卷纲、细纲和情节节点的规划工作区。
- 选择“伏笔库”时，右侧进入伏笔列表、生命周期、埋入/回收记录和标记来源管理工作区。
- 选择“线路规划”时，右侧进入线路列表、线路关系、推进状态和交汇节点工作区。

切换界面时应保留当前作品和 Agent 会话；当前页面的筛选、展开节点、选中对象和未提交编辑是否保留，需在后续交互合同中明确。Agent 应能感知当前选中的三段式页面，并把用户对话与当前工作区对象关联起来。

### 初步布局取舍

- 采用左侧常驻 Agent，而不是独立弹窗或单独页面，是为了让用户在浏览和编辑规划对象时始终能够获得即时协助。
- 采用右侧单工作区加三段式切换，而不是同时平铺三个复杂面板，是为了保持规划对象的专注编辑空间，避免首屏信息过载。
- 三段式导航只负责一级能力切换；伏笔埋入与回收管理作为贯穿大纲库、伏笔库和线路规划的横向能力，不额外占用一个一级导航段位。

## 本轮确认的设计决定（问题一：前 10 项）

本节记录前一轮对问题一中前 10 个核心问题的确认结果；其中第 9、10 项曾未确定，本轮答复已在下文“本轮补充决定（二至八）”中补全。提案仍非已生效实现合同。

### 1. 多条大纲链的性质

- 多条大纲链用于表达同一作品的不同整体走向，类似“方案 A／方案 B”，而不是天然代表主线、支线或角色线。
- 每条大纲链采用“全局总纲 → 卷纲 → 章节大纲”的关系结构；全局总纲对象只有一个。
- 不同大纲链之间允许复用条目；用户界面上的“复制”在文件层面表现为同一个条目被多个位置引用，不创建内容副本。
- 复用条目默认保持同一条目被多个位置引用；用户修改被复用条目时必须先弹窗确认，确认后在当前修改位置建立全新稳定 ID 和不同文件名的独立文件，原文件及其他引用位置不受影响，且不提供重新合并回共享条目的操作。

### 2. 总纲、卷纲、章节大纲和细纲的关系

- 全局总纲只能有一个；作品可以拥有多条代表不同走向的方案链，各方案链通过关系引用同一个总纲，并分别组织卷纲和章节大纲。
- 每个总纲下允许多个卷纲，每个卷纲下允许多个章节大纲。
- 一个章节大纲通常关联一个细纲，也允许关联多个按场景拆分且相互连贯的细纲。
- 原则上不允许没有对应章节大纲的独立细纲；允许章节大纲暂时没有细纲。
- 章节大纲与正文采用一对一关系。
- 细纲保存时由用户选择保存为草稿或正式文本：草稿无需 AI 分析，也不进入正式写作使用范围；正式文本保存前必须完成 AI 偏差与冲突分析，并提示用户查看结果。
- 分析发现偏差时，讨论模式允许修订重试或用户确认带警告保存；自动模式可带警告保存并提供撤销，不额外审批；分析失败或未完成不能当作通过校验。

### 3. 大纲标签模型

采用分离设计：

- 采用状态：草稿、正式采用；
- 行为标签：埋设伏笔、回收伏笔，可叠加；
- 因此同一章节大纲可以同时是正式采用、埋设伏笔和回收伏笔。

### 4. 伏笔标记规则

- 用户界面使用类似文档注释的下划线标注，鼠标悬停显示关联信息。
- 系统层面使用 Markdown 结构化文本保存标记。
- 一个章节允许多次埋设同一伏笔；同一伏笔也允许在多个章节中多次强化。
- 一般不建议同一章节同时埋设和回收同一伏笔，但允许用户明确这样规划。
- 不允许在没有有效埋设记录时先产生有效回收记录。
- 标记删除后，程序重新解析并自动更新伏笔状态。
- 讨论模式下 Agent 建议标记在用户认可前只保存为草稿或建议；自动模式中获得持续授权后可直接采用非删除标记并参与正式状态计算，仍可撤销。

### 5. 伏笔状态语义

按此前建议保留四种主要状态，但明确它们是规划层状态：

- 草稿；
- 待使用；
- 已埋设；
- 已回收。

“已回收”仅表示大纲规划中已经存在有效回收标记；正文是否完成不属于伏笔库状态，也不建立正文证据状态来覆盖或改变该结果。

### 6. 线路节点与大纲条目的关系

- 线路节点和大纲条目是两个不同的数据对象和表现形式。
- 一个线路节点只表示一个大纲条目，具体关联对象由用户设定。
- 一个节点允许与多个其他节点连接；主线和 IF 线方向分别对每个节点限制为至多一条。
- 大纲条目被删除或修改时，引用它的节点必须被程序标记：删除为红色，修改为黄色。
- 被删除条目对应的节点必须重新关联有效大纲条目后才能使用；被修改条目对应的节点必须重新通过 AI 冲突分析后才能作为已确认节点使用。

### 7. 伏笔多次埋设与回收前置条件

- 同一伏笔可以多次埋设和强化。
- 有效回收必须以存在有效埋设为前提。
- 伏笔状态根据当前有效章节标记动态计算；删除或失效标记后状态自动重新计算。

### 8. 线路结构和时间顺序

- 线路图采用树状图的呈现方式，主干通常为当前正式规划版本的主线，枝干可以是支线、角色线或 IF 线。
- 一个节点可以同时成为主线、支线、角色线和 IF 线等多种线路的起点。
- 一个节点允许被多个节点同时连接，关键转折节点可以拥有多条入边。
- 从左到右是严格的剧情顺序，也表示时间线顺序。
- 每个正式规划版本最多设置一条主线；草稿版本可以暂时没有主线。切换主线时保留原节点链，但取消其主线属性。
- 由于允许多入边，数据模型不能简单实现为严格树，应保存为带线路类型的有向图；默认不允许形成环，是否允许特殊回溯环仍需明确。

### 9. Agent 写入审批

支持讨论与自动两种模式。讨论模式下 Agent 正式写入需要用户确认（批量可一次确认）；自动模式下非删除的模块内操作无需逐次审批，包括正式伏笔引用。删除对象、解除引用等删除行为在两种模式下均须审核；总纲删除还须二级确认。每次已执行操作或批次应提供撤销按钮，撤销不能静默覆盖后续修改。

### 10. 文件与数据库真相源

结构化项目文件是规划数据的唯一规范来源，SQLite 仅作为可重建索引、查询加速数据和解析摘要。采用 `outline/manifest.yaml`、`outline/entries/*.md`、`outline/foreshadowing/*.md` 与 `outline/lines/*.yaml` 的目录布局；UI 写入与外部文件编辑均经过校验和重解析，检测冲突时不静默覆盖。具体 schema 字段、事务边界和版本迁移仍由 Phase 0/1 的实现合同细化，但不得改变文件优先和索引可重建原则。

## 本轮补充决定（二至八）

### 二、模块 Agent 的权限模式

- 提供讨论模式与自动模式。讨论模式先讨论和展示变更，用户确认后执行；批量操作展示完整范围后可一次确认。
- 自动模式由用户明确启用，在本模块内的非删除操作无须逐项审批，包括 Agent 提议的正式伏笔标记；执行后展示摘要、来源与结果，提供撤销按钮。
- 删除对象、解除引用等删除行为在任何模式下都需要审核；总纲删除在影响预览之外再进行二级确认。自动模式不授予正文或其他模块的写权限；`lorebook/` 只能由受委派的专用子 Agent 写入（2026-09-26 起）。
- 撤销按操作或批次执行，须同步恢复文件与派生状态；出现后续更改或文件冲突时不能静默覆盖。

### 三、持久化默认方向

结构化项目文件是规划真相源，SQLite 只作为可重建索引、查询加速数据和解析摘要。采用 `outline/manifest.yaml`、`outline/entries/*.md`、`outline/foreshadowing/*.md` 与 `outline/lines/*.yaml` 的目录布局；UI 有效编辑校验后写文件并更新索引，外部文件变更重解析，冲突不静默覆盖，解析失败保留原文。具体 schema 字段、事务边界和版本迁移仍由 Phase 0/1 的实现合同细化，但不得改变文件优先和索引可重建原则。

### 四、标记、伏笔与正式保存默认方向

- 标记使用稳定 ID、引用目标、动作与位置锚点；只从有效的正式章节大纲标记计算伏笔规划状态。异常有独立告警，不默认为有效标记。
- 伏笔规划状态只由正式大纲条目中的有效埋设和回收标记派生；不读取正文，也不额外建立正文回收状态。
- 细纲保存为正式文本前必须进行 AI 偏差和冲突分析；有问题时展示证据，讨论模式由用户决定修订或带警告保存，自动模式可带警告保存并提供撤销；分析失败不能视为通过，两种模式均不得豁免分析。

### 五、线路的默认校验分工

- 主线唯一性在单一设置入口和数据约束中保证，不把“两条主线冲突”交给 AI；切换主线保留原节点链，仅移除其主线属性。
- 程序检查引用、重复、断链、时序逆转和成环；重复节点会阻止线路固定和正文编写，必须处理后再进行冲突分析；线路图按有向无环图保存，节点链成员按从左到右连续可达选取；AI 仅分析剧情因果、人物状态等语义冲突。
- AI 分析结果绑定输入版本；被引用大纲修改后节点标黄，旧结论失效，当前版本重新分析后才恢复使用。正常 UI 删除因“引用锁”应被阻止；外部修改或旧数据造成缺失引用时仍以红色异常节点提示修复。

### 六、`writer.pro` 的单向交接

`writer.pro` 对本模块只读，且只能读取当前线路规划中被正式采用并已关联的内容：线路规划所引用的正式章节大纲、对应正式细纲、本章正式伏笔标记处的文本和线路上下文；伏笔定义中的背后关联和回收计划不交给正文。线路规划中的内容才是最终用于编写正文的大纲条目；未被线路规划引用的正式大纲、草稿、Agent 建议和待确认变更均不进入正文写作上下文。它不能修改、删除或推进本模块的任何对象和状态，发现冲突只能回报用户或本模块。其正文写入权限由正文模块单独管理。

### 七、删除、引用与级联影响

- 总纲可删除，但必须先预览级联影响并二级确认；其他对象删除也必须先预览所有受影响的下级、细纲、伏笔标记、线路节点和正文关联。
- 被引用的对象锁定，不允许直接删除；UI 提示引用位置并引导用户先解除关系，关系解除与对象删除分别确认和记录，不允许静默级联。
- 移动、重排或解除某个引用不会改变条目的稳定 ID；多位置引用同一实体时，只解除指定关系不误删共享实体。

## 原始设计补充（2026-09-26 确认）

以下内容取自《新小说编写计划》原始设计，开发者确认按主 Agent 建议并入本模块。对照过程见 [原始设计对照整理](../../.agents/works/w00018-outline-planning-module/original-design-reconciliation.md)。

### 大纲库与细纲

1. **卷纲与章节大纲的骨架要素**：写明起点、主要发展、关键事件、转折和阶段落点。方向生成和 `outline` 子 Agent 按此组织草案。
2. **细纲正文的内容要素**：细纲正文覆盖以下内容：
   - 本章承接的局面、主要内容和结束位置；
   - 场景顺序、人物行动、事件发展和场景衔接；
   - 必须呈现的细节、对白意图、信息披露和已有伏笔安排。

   先作为内容清单，供 `Detailed outline` 子 Agent 生成草案，也供正式保存前的偏差分析检查缺项，暂不拆成结构化字段。
3. **细纲的详细程度**：细纲完成必要的剧情决定，但保留语言表达空间，不逐句指定正文措辞。
4. **写作指导**：按场景或片段锚定，推荐说明哪些内容展开、哪些略写，采用什么手法，重点表现什么。（实现进度：已完成场景注释的解析与交接，工作台编辑已在一.1 完成）
5. **参考文件**：每条标注写明资料、所用部分和用途。没有实际可查阅来源的资料标记为”待补”，不得编造路径或内容。”待补”不阻止细纲正式采用，但要在偏差分析结果和正文交接中作为告警出现；`writer.pro` 遇到”待补”不得自行补写相关知识。（实现进度：已完成 schema、分析与交接告警，工作台编辑已在一.1 完成）
6. **篇幅**：支持章节总目标字数，必要时按场景分配大致字数。（实现进度：场景字数随写作指导注释的 `words` 属性表达，已完成解析与交接）
7. **界面展示**：章节大纲详情中可同时查看其细纲及标注；线路节点显示关联条目的层级和细化情况（是否已有正式细纲），便于判断能否固定。

### 伏笔库

8. **伏笔设计内容**：每条伏笔包括：
   - 名称；
   - 表面呈现的线索与背后的关联，二者分开保存；
   - 埋设建议：出现情境、呈现方式、暗示程度；
   - 回收建议：揭示条件、前后呼应方式、预期效果。
   
   （实现进度：已完成 schema 与接口，字段为 `surface`、`connection`、`plant: {situation, presentation, subtlety}`、`recover: {condition, echo, effect}`，工作台编辑已在一.1 完成）
9. **已过章节数**：作为派生指标，不是第五种状态，用于发现超期未回收的伏笔。（实现进度：已完成派生与接口，工作台卡片只读显示）
   - 章节顺序只来自线路规划，因此按方案计算：取该方案下已固定线路中章节节点从左到右的顺序；
   - 起点为首个有效埋设所在章节；未回收时终点为该线路最后一个已固定的章节节点，已回收时显示埋设到回收的间隔；
   - 不以正文完成情况计数；章节重排或线路改动后重新计算；
   - 同一伏笔出现在多个方案时，分方案显示。
10. **状态只经标记改变**：Agent 只能通过增删改正式标记间接改变伏笔状态，不能直接写状态或派生字段。
11. **依据派生状态提出建议**：`foreshadowing` 子 Agent 结合当前派生状态和已过章节数调整建议，例如优先为长期未回收的伏笔给出回收建议。

### Agent 与交接

12. **按任务范围授权**：见“模块 Agent 的权限与职责”，两种模式都不超出用户当前指令的范围。
13. **只交接本章所需的伏笔信息**：正文交接只包含本章标记处的文本，以及细纲、写作指导中落实的呈现要求；不包含伏笔定义中的背后关联和回收计划，以免正文提前泄露后续剧情。

- **模块级配置对象**：当前没有需要单独配置的项，以后出现再纳入 manifest，并单独记录变更。
- **显示用短编号**（如“伏笔 F-12”）：稳定 ID 已能满足引用需求，如用户在对话中确有需要再补，且不替代稳定 ID。

## 与规划素材和正文写作的关联

### 规划素材目录与按需读取

大纲规划模块 Agent 可读取当前项目的 `lorebook/`，用于理解角色、势力、风格、物品、地点、规则和世界观。当前设计沿用旧文档中已明确的素材分类：

| 素材类别 | 来源目录 | 主要用途 |
| --- | --- | --- |
| 角色人设 | `lorebook/character/` | 身份、性格、经历、能力和行为依据 |
| 势力设定 | `lorebook/faction/` | 背景、目标、结构、立场和相互关系 |
| 风格基调 | `lorebook/instruction/` | 整体基调、表达倾向和创作约束 |
| 特殊物品设定 | `lorebook/item/` | 外观、来源、能力、限制、使用条件和表达基调 |
| 地点设定 | `lorebook/location/` | 环境、功能、历史和空间关系 |
| 写作指导与参考资料 | `lorebook/note/` | 既有写作指导、知识说明和参考资料 |
| 特殊规则 | `lorebook/system/` | 世界运行规则、能力规则、系统限制和例外条件 |
| 世界观设定 | `lorebook/world/` | 时代背景、社会结构、基础设定和世界整体框架 |

读取规则为：Agent 先分析本轮任务，再选择所需素材类别和具体文件；用户明确指定文件或目录时优先按指定内容读取；不默认将全部素材加载进上下文。素材索引应保存可稳定解析的文件或素材标识，而不是只保存显示名称。读取素材不等于获得修改素材的权限，规划产物写入也不改变 `lorebook/` 的所有权；只有受委派的专用子 Agent 可以写入 `lorebook/`，见“模块 Agent 的专用子 Agent”。

### 向 `writer.pro` 的交接

大纲规划模块向正文写作 Agent `writer.pro` 提供已确认的章节大纲、细纲、写作指导、参考文件和篇幅要求，并通过稳定 ID、文件定位和版本信息交接。`writer.pro` 对本模块只有读取权限，没有创建、修改、删除、审批、移动、重排、标记或状态推进权限；它只能读取“正式采用”的大纲、细纲、线路和本章正式伏笔标记处的文本，草稿、Agent 建议、待确认变更、未采用内容以及伏笔定义中的背后关联和回收计划不在读取范围内。需要在正文中呈现的伏笔，由细纲和写作指导落实。作品既定的人称与文风可以来自用户或作品级配置；本模块负责提供章节级规划和标注，不复制正文或另建一份写作真相。

`writer.pro` 的主要输入仍包括：主要视角、字数要求、文风参考、细纲、写作指导和参考文件。其边界是组织语言、对话和描写，不改变既定事件、人物选择、信息披露和结尾落点；伏笔规划账本、线路类型和正式大纲状态由本模块维护。若正文写作发现剧情缺口或输入冲突，应反馈给用户或本模块，不自行回写正式规划。

大纲中的“已回收”只表示存在有效的正式回收标记，不代表正文已经写完；`writer.pro` 读取到的只能是线路规划中确认固定的正式采用内容。正文写作不参与伏笔状态计算，若用户发现需要调整规划，应回到大纲条目或线路规划中通过用户或授权 Agent 处理。

## 数据、接口、安全、迁移、发布与回滚影响

- **数据边界**：需要复用现有作品、章节、正文、实体、历史和 Agent 会话的身份与所有权，不能为大纲模块另建互相覆盖的平行数据源。
- **持久化**：大纲、伏笔、线路、证据和 Agent 建议很可能需要可版本化、可审阅的持久化记录；具体 schema、迁移和索引待方案确认后确定。
- **写入权限**：模块 Agent 根据讨论模式或自动模式操作；自动模式允许非删除的正式规划变更，所有删除均需审核，批量确认一次覆盖明确展示的范围并提供撤销。模块 Agent 不获得正文写入权限；`writer.pro` 对本模块只读且只读正式采用的内容。
- **正文关系**：本模块只向正文模块交接线路规划中已固定的正式章节大纲及其上下文，不以正文内容作为伏笔埋设或回收状态的来源。
- **迁移**：本期不提供从旧笔记或《新小说编写计划》导入规划的功能；如以后需要从用户已有笔记导入，另立 Proposal。
- **发布与回滚**：当前仅做产品规划，不涉及发布或远端写入授权。实现前需定义版本兼容、数据备份、迁移失败恢复和规划变更回滚。

### 已确认设计决定

1. **[已确认] 大纲链模型**：多条方案链用于同一作品的不同整体走向，类似方案 A／方案 B；方案之间是完全不同的作品展开，但共同引用唯一全局总纲。允许跨方案复用同一条目，但复用条目被修改时采用写时分叉：当前修改位置保存为独立新文件，原文件及其他引用位置不受影响。IF 线不属于方案链，而属于线路规划内部的分支线路。
2. **[已确认] 层级模型**：全局总纲只有一个；每条方案链通过关系引用该总纲，并可拥有多个卷纲和章节大纲；细纲依托章节大纲存在，可为一个或多个连贯场景细纲。
3. **[已确认（采用默认建议）] 生成流程**：用户输入简单方向后，Agent 默认先生成可审阅的草案；用户可以选择只生成总纲、继续生成卷纲和章节大纲，或分阶段逐级生成。生成结果先进入草稿，支持局部修改、重新生成和保留用户编辑；讨论模式经用户确认、自动模式依持续授权采用后才转为正式。
4. **[已确认] 最小单元**：章节大纲与正文一对一；细纲可拆成多个连贯场景片段；草稿细纲不进入正式使用，正式细纲保存前触发 AI 偏差与冲突分析。
5. **[已确认] 规划与正文关系**：章节大纲与正文是一对一关系；规划偏离不应由正文 Agent 静默改写，应形成偏差或待确认建议。
6. **[已确认（采用默认建议）] 线路模型**：线路图以树状图呈现，主干为主线、枝干可为支线、角色线或 IF 线；IF 线用于表现某一方案内部由分支导致的不同走向和结局起点。数据层按带类型的有向无环图处理，允许关键节点多入边和多线交汇；程序负责结构校验，AI 负责语义冲突分析。线路状态机、优先级和交汇节点的扩展字段留待数据合同细化。
7. **[已确认] 线路图数据模型**：节点与大纲条目为不同对象，一个节点关联一个大纲条目；每个方案的节点、连线和格号、行号保存在 `outline/graphs/<slug>--<stable-id>.yaml`，线路（类型、固定状态、勾选节点、分析报告）保存在 `outline/storylines/<slug>--<stable-id>.yaml`；格号是业务顺序，行号只是排版。文件是规范来源，SQLite 为可重建索引。（2026-09-26 修订：取代每条线路自带节点与边的 `outline/lines/` 设计，旧文件不兼容。）
8. **[已确认] 主线唯一性**：每个正式规划版本最多允许一条主线节点链；草稿版本可以暂时没有主线。每个节点至多一条主线方向连接，IF 线同理。由单一设置入口和数据约束保证，不作为 AI 冲突检查项；切换主线时原链保留但失去主线属性。
9. **[已确认（采用默认建议）] 节点链选择**：用户逐个勾选节点设置节点链时，要求所选节点按格号排序后相邻节点之间都有连线；允许不同线路在关键节点交汇并复用节点，不允许通过跳跃节点或环路伪造连续链。
10. **[已确认] 节点顺序**：从左到右是严格剧情顺序和时间线；允许分支、汇合和多入边；数据层默认禁止环，回忆、倒叙等特殊时间线通过节点内容表达，不改变线路的正向剧情顺序。
11. **[已确认] 重复节点处理**：程序根据稳定 ID、关联大纲条目和结构特征标注重复；重复节点不能用于剧情编写或固定为正式线路，用户必须处理重复关系并重新完成冲突分析后才能继续使用。系统不静默删除对象，用户可查看重复来源并处理关联。
12. **[已确认（采用默认建议）] AI 冲突分析**：程序负责引用失效、重复标识、断链、逆序和成环等确定性检查；主线唯一性由设置入口和数据约束直接保证，不单列为冲突分析；AI 负责因果、人物状态、节奏和语义冲突分析。AI 结果属于带证据的检查建议，不自动改写正式内容；用户可以确认已处理、忽略并记录理由，或转为待办事项。
13. **[已确认] 伏笔状态边界**：伏笔状态由全部有效正式大纲标记汇总动态计算，不按大纲链或方案拆分；回收必须先有有效埋设，删除或失效标记后自动重算。伏笔条目保留埋设和回收标记来源，供用户追溯具体大纲条目和线路节点。系统只保留草稿、待使用、已埋设、已回收四种状态；标记异常通过独立告警呈现，不扩展为其他生命周期状态。
14. **[已确认（采用默认建议）] 异常标记处理**：无埋设先回收、引用不存在、格式损坏时保留原文与上次有效投影，标出可定位异常；不得把异常作为正式有效伏笔标记，也不得静默当作删除。结构错误阻止受影响对象进入正式采用；修复后重解析。
15. **[已确认] 伏笔生命周期**：伏笔库只使用草稿、待使用、已埋设、已回收四种状态。标记损坏、引用失效或回收顺序错误属于异常信息，不作为第五种状态，也不改变四种状态的定义。
16. **[已确认] 证据定位**：伏笔埋设与回收状态不使用正文证据或正文定位；状态只从正式大纲条目中的有效标记获取和确认。正文证据定位不属于本模块的状态合同。
17. **[已确认] 版本与分支**：多条大纲链承载方案 A／方案 B 等完全不同走向；跨方案复用条目采用写时分叉，修改位置保存为独立新文件，原文件和其他引用不被同步修改。版本与快照采用当前实现：`outline/manifest.yaml` 的 `revision` 作为规划快照序号，每个对象另有自己的 `version` 与内容 hash；写入以 revision + 对象版本/hash 做 CAS，冲突时拒绝并要求重新读取，不使用隐含覆盖。撤销以事务为单位（一次操作或一个批次），撤销与后续修改冲突时返回冲突而不是强制覆盖。正式线路的选择在“线路规划”中完成：用户在节点图上设置线路类型并执行“固定”，固定后的节点构成正文使用范围；切换主线时保留原节点链但取消其主线属性。草稿和未进入线路规划的内容不供 `writer.pro` 读取。
18. **[已确认] Agent 写入权限**：支持讨论模式和自动模式。讨论模式下非删除变更需用户逐项或按批次确认；自动模式下模块内非删除操作可直接执行。批量操作一次确认已展示的明确范围即可；删除、解除引用和总纲删除始终需要用户审核，总纲删除还需二级确认。所有执行结果保留变更摘要、日志和撤销按钮。
19. **[已确认] 上下文装配**：`writer.pro` 只读当前线路规划中正式采用且与本章关联的内容：本章章节大纲、对应正式细纲、本章伏笔标记处的文本、素材索引和参考文件定位，以及线路上下文。选择粒度按章节：调用方以线路 ID 加版本锚点请求，返回该线路按从左到右顺序的节点及其所属章节上下文，不返回整库内容。草稿、建议、未进入线路规划的内容，以及伏笔定义中的背后关联和回收计划都不在读取范围内。上下文规模由章节数量决定，不默认截断；参考文件内容由调用方按需读取。参考文件标记为“待补”时随结果返回告警。冲突处理遵循第 20 条：由用户决定，或委托获得授权的 Agent 在授权范围内处理。
20. **[已确认] 冲突处理**：规划、正文、人物设定、世界观和不同线路出现矛盾时，由用户决定如何解决，也可以委托获得授权的 Agent 处理；Agent 只能在授权范围内执行，结果需保留依据、变更记录并支持撤销。
21. **[已撤销（2026-09-26）] 迁移策略**：此前的设计把《新小说编写计划》这份开发设计文档当作用户规划数据导入，属于误读，相关功能已删除。本期不提供旧笔记导入；如以后需要，另立 Proposal。
22. **[已确认] 标注格式**：用户界面使用下划线注释并悬停查看关联信息，文件层使用 Markdown 注释包围可见文本的结构化标记，动作限定为 `plant`、`reinforce`、`recover`，并保存稳定标记 ID、伏笔 ID 和可定位来源。标记损坏、未知 ID、未知动作或未成对注释不得静默成为正式事件；解析失败保留原文并标出异常。
23. **[已确认] 同步语义**：正式大纲条目标记保存后重解析并刷新派生伏笔状态；草稿与建议不参与，正文内容不参与状态计算。引用不存在或标记损坏时提示异常，可在 Agent 界面请求 Agent 分析修复；因条目被引用而无法直接删除，须先展示影响并解除关系，最后删除对象。持久化事务边界采用当前实现：一次操作或一个批次在同一个事务内写入全部规范文件与历史记录，全部成功才发布，任一文件失败则整批回滚并保留原文件。批量操作按一次可撤销变更处理，撤销与后续修改冲突时拒绝。
24. **[已确认] 标签模型**：采用状态与行为分离的两套字段；草稿／正式采用是采用状态，埋设伏笔／回收伏笔是可叠加行为标签。
25. **[已完成] 验收指标与开发规划**：已建立 `w00018-outline-planning-module` Work、合同与架构 Task、六项 planned Spec 和分阶段实施计划；当前不进入产品代码实现，下一步先完成 Phase 0 的领域映射与实现合同。
26. **[已确认] 界面布局与 Agent 控件**：模块采用全屏左右分栏；左侧常驻 Agent 对话区从顶部贯穿到底部，默认约占窗口宽度 `1/5`，右侧工作区约占 `4/5`；左右栏支持通过分隔线拖拽调整，左侧 Agent 区域最大不得超过窗口中线，即宽度不超过 `1/2`。当前阶段不做小屏、窄屏或移动端适配。输入框下方提供思考开关、模型选择、温度设置和讨论／自动模式切换，其中思考开关使用两段式按钮，模型设置使用列表，温度设置使用数值框和调整按钮，不使用滑块；上下文列表支持流式呈现 AI 输出。左右栏布局状态按当前项目持久化，重新进入项目、重新打开项目或重载 UI 后均恢复已保存布局。右侧顶部居中提供“大纲库／伏笔库／线路规划”三段式切换。

## 补充建议

以下保留供后续细化参考；与前文已确认的默认方向重合时，以前文决策为准，不把尚未确定的字段或实现细节视为已批准合同：

- **先建立统一的“规划节点”基础对象**：总纲、卷纲、章节大纲、细纲、线路和章节计划尽量通过稳定的节点与关系连接，避免每个页面各自定义一套不可互通的数据。
- **将多条大纲链显式建模**：为每条链设置稳定身份、名称、用途和当前状态；删除或修改一条链时不影响其他链，并为从草案链切换到正式链保留清晰的确认记录。
- **把正文标注视为领域语法**：用户看到的是注释式交互，文件中保存的是可解析的结构化标注。标注需要有稳定身份、引用目标、位置锚点和版本信息，解析失败时保留原文并产生待处理错误，而不是静默删除或错误同步。
- **区分索引继承和局部覆盖**：细纲默认继承章节大纲的素材索引，但应能明确追加、移除或覆盖，避免 Agent 无法判断某份素材是否适用于当前细纲片段。
- **把篇幅要求拆成可执行约束**：除了章节总字数，后续可支持细纲片段的字数分配、上下限和偏差提示，让写作 Agent 能据此控制输出，而不是只在写作完成后统计字数。
- **将大纲标签拆为状态与能力标记**：建议把“草稿/正式采用”作为生命周期状态，把“埋设伏笔/回收伏笔”作为可叠加的内容能力或事件标签，以支持同一条目同时处于正式采用且承担两类伏笔动作。
- **把伏笔状态设计为可解释的派生状态**：伏笔库显示状态应能跳转到产生该状态的埋设/回收标记和来源大纲，避免用户只能看到“已埋设”而无法知道是哪一章、哪一处标记导致的判断。
- **区分正式标记与 Agent 建议标记**：讨论模式尚未审批的引用保留在建议或草稿层；自动模式依授权采用后可成为正式标记。解析器只读取当前有效正式标记，不把未采用建议误算为伏笔状态。
- **为伏笔状态计算保留异常通道**：正常状态只有草稿、待使用、已埋设、已回收，但解析异常、标记损坏和逻辑矛盾应通过告警或独立异常结果呈现，不能强行归入正常状态。
- **支持多次埋设与一次或多次回收**：同一伏笔可能在多个章节重复强化或分阶段回收，状态不应只保存单一章节字段；应保留事件集合，并根据是否存在有效回收事件计算汇总状态。
- **将线路图保存为可重建的结构化图**：节点、边、节点链和线路类型都使用稳定标识保存，图形坐标作为布局信息而不是唯一的剧情事实；这样可以在文件损坏或界面重排后恢复业务关系。
- **分开“关联节点”和“节点链成员”**：某个节点可以关联大纲条目，但不代表它已经属于某条正式线路；用户完成节点链类型设置后再形成明确的线路归属，避免临时节点污染主线判断。
- **程序先做确定性检查，AI 再做语义检查**：重复标识、断链、主线超过一条、引用失效等结构问题由程序直接判断；因果冲突、人物状态矛盾和节奏问题由 AI 提供带证据的分析建议。
- **为节点链分析建立可追溯结果**：每次 AI 分析记录分析范围、输入版本、结论、证据节点和处理状态，避免线路修改后旧结论被误当作当前事实。
- **把重复节点设计成标注而非自动删除**：重复可能是有意的多线复用，也可能是误建节点，保留用户确认空间比自动合并更安全。
- **把规划标记设计为可解释来源**：伏笔状态只来自正式大纲条目，至少保留来源条目、标记动作和解析结果，便于复盘和修复。
- **优先提供可解释的待处理清单**：首版价值可能不在复杂图谱，而在“本章涉及哪些规划”“哪些伏笔待回收”“哪些线路停滞”“哪些变更会产生影响”等可直接行动的结果。
- **建立变更影响预览**：修改一个节点、线路或伏笔时，先显示受影响的章节、线路、标记和 Agent 上下文，降低规划调整造成的连锁误写风险。
- **为 Agent 设计建议层**：建议、草稿、已确认和已发布/生效最好有明确区分，并保留来源与版本，避免模型生成内容悄然成为产品事实。
- **首版采用渐进结构化**：允许先保存自由文本，再逐步提取节点、关系和伏笔标记；但每次结构化结果都要可审阅、可回退，不强迫用户一次完成全部建模。
- **从规划交接闭环验收，而不是从页面数量验收**：至少验证“规划本章 → 线路固定正式节点 → 写作前获得相关上下文 → 用户确认规划变更”的完整路径。
- **明确单一所有权**：大纲库、伏笔库和线路规划可以在同一模块展示，但应提前定义各自的写入 owner，避免正文、记忆库、Agent 会话和规划模块互相覆盖。
- **把常驻 Agent 做成模块级宿主**：Agent 会话、当前作品、当前规划版本和当前选中对象应由模块级状态管理，不能由三个右侧页面分别维护。
- **权限按能力而不是按页面授予**：三段式页面只是展示入口，Agent 的读写权限应由大纲规划领域服务统一控制，避免通过切换页面绕过权限或产生不同写入语义。
- **当前不做窄屏退化**：本阶段只定义全屏桌面布局和可拖拽分栏，不为小屏、窄屏或移动端增加侧栏折叠、抽屉化或其他响应式适配；后续若重新提出适配需求，应单独评估布局、会话保持和交互边界。
- **让 Agent 与工作区联动但不被页面绑死**：Agent 应读取当前页面和选中对象作为上下文提示，同时允许用户明确指定跨页面查询，避免只能操作当前标签页。
