# Inspiration 作品大纲提取与大纲库接轨

状态：accepted。大纲库接轨、素材提取类别、流程、模板与确认方式已由开发者于 2026-10-01 逐项确认；工作台 UI 整理不在本文范围，另行讨论。

## 问题

设计模块的初衷是服务改编：把原作的大纲、细纲提取出来，便于 AI 理解情节并改编。当前首版只把大纲、细纲作为 `note` 类“写作指导与参考资料”保存，没有进入大纲库，无法被大纲模块和写作模块按方案使用。

同时，大纲库实现为“全局唯一总纲、所有方案共享”，偏离了“每个方案各有一个总纲”的原始设计，提取出的原作总纲无处安放。

## 目标与非目标

目标：

- 修复大纲库总纲合同：每个方案恰好一个总纲，方案之间默认互不共享。
- 新增程序化的作品大纲提取流水线：章节识别、用户划卷、预建方案结构，按“原文 → 细纲 → 章纲 → 卷纲 → 总纲”自下而上填充大纲库。
- 提取任务后台运行、可见进度、单章失败可单独重试；支持重复提取时选择数据去向并对比确认。
- 将素材提取重构为与大纲提取分开的程序化流水线，类别调整为九类，按实体型、文档型、逐条收录三种模式处理，结果写入 `lorebook/` 并标记来源。

非目标：

- 原创设计不接入大纲库；大纲与伏笔的原创规划由大纲模块自身负责。原创设计的八类专业方向不变。
- 不处理工作台 UI 整理；UI 整理在其他改动完成后单独进行。
- 不改变写作模块“按所选方案写作”的行为。

## 当前行为与证据

- 切分：[`server/inspiration/source-split.ts`](../../packages/neuro-book/server/inspiration/source-split.ts) 已识别“第X章/回/节/卷”、`Chapter N`、序章/楔子/尾声/番外等标题，并以完整章节为不可分单位组成约五万字的块；章节不作为用户可见的主单位，不识别纯数字标题，不支持人工修正，且把“第X卷”当作章节标题。
- 提取：[`server/inspiration/service.ts`](../../packages/neuro-book/server/inspiration/service.ts) 在一次同步请求内逐块调用 `inspiration.extract` Agent，受十五分钟总超时约束；任一块结果越界即整体失败，已完成块的成果丢失。
- 总纲：[`server/outline/format.ts`](../../packages/neuro-book/server/outline/format.ts) 以 `manifest.totalId` 表示全局唯一总纲，并要求每个方案以它为根；建方案、删除级联、写作交接、Agent 工具、大纲界面与测试共约 34 个文件依赖此字段。
- 写作方案：[`server/writing/host.ts`](../../packages/neuro-book/server/writing/host.ts) 将所选方案存为 `writingPlanId`，章节目录与上下文均按该方案读取，已满足“选哪个方案就用哪个方案写作”。
- 细纲审阅：[`server/outline/writer-context.ts`](../../packages/neuro-book/server/outline/writer-context.ts) 的 `assertDetailReviewed` 要求正式细纲带有绑定方案的偏差分析报告；上游链变化时已采用细纲退回草稿。
- [`planning-library.md`](../specs/outline/planning-library.md) 写明“不提供从旧笔记或设计文档导入规划的功能”。

## 方案、备选方案和取舍

### 一、大纲库总纲合同

每个方案恰好一个总纲。新建方案时默认新建独立的空总纲；只有用户或 Agent 手动建立关联后，方案之间才共享同一总纲条目，共享后的修改沿用现有写时分叉。已有项目中共用总纲的方案保持共享关系，数据无需迁移，只去除全局唯一约束。

放弃的备选：提取结果放入独立“参考规划”空间。原因是总纲合同本身需要修复，修复后提取方案即普通方案，可直接被写作模块选用、被大纲模块编辑。

### 二、章节识别与划卷

- 用户选择来源后程序立即识别章节并显示章节列表（标题、P 段落范围、字数）。识别规则补充单独一行仅有数字等常见形式，并支持用户修正识别结果；“第X卷”识别为卷标题，作为默认划卷建议。纯数字行等易误判规则需要结合上下文判定，具体规则在 Spec 中定义。
- 章节模式：用户指定章节范围为各卷，也可整部作品为一卷。
- 字数模式（无可识别章节）：用户设置每 N 个切分块为一卷；一块对应一章，即一份细纲和一份章纲。

### 三、提取流水线

提取是纯程序流水线，不由 Agent 编排。程序负责切分、调度模型调用、解析校验、写入大纲库与记录进度；Agent 只能向流水线下发任务或确认流水线成果。

1. 按划卷结果新建方案，预建空的总纲、卷纲与章节大纲结构。
2. 逐章提取细纲：输入本章原文。
3. 逐章提取章纲：输入本章原文与本章已提取的细纲。
4. 按卷汇总卷纲：只输入本卷全部章纲，不读原文。
5. 汇总总纲：只输入全部卷纲。

细纲与章纲分为两条工作流，避免原文过长时同时输出两者导致内容失真。为利用提示词缓存，各工作流共用同一份系统提示，提示词前缀统一为本章原文，细纲等追加材料放在原文之后，任务目标放在末尾。

流水线作为后台任务自动跑完全程，界面显示整体与逐章进度；任务以章为单位记录状态，单章失败只重试该章，不丢弃已完成成果。条目与引用沿用现有 P 段落编号，原文范围记入大纲条目的 `references.locator` 以保证可追溯。

放弃的备选：每章一次调用同时产出章纲与细纲（输出过长时失真）；卷纲汇总回读原文（上下文过长，且不符合自下而上）。

### 四、提取条目的正式状态

流水线写入的条目直接为正式条目。提取细纲新增“来源提取”采用依据：以原文引用为依据，免偏差分析；“上游变化即退回草稿”的规则不适用于这类细纲，因为其依据是原文而非上游规划。用户手动编辑提取细纲正文后，该细纲转为普通细纲，适用常规分析审阅规则。

放弃的备选：细纲仍需审阅（与“直接正式”矛盾）；流水线自动跑偏差分析（分析对象本身由同一原文提取，意义有限）。

### 五、重复提取与数据去向

重复提取时用户选择数据去向：

- 新建方案：命名为“提取方案N·<作品名>”，N 依次递增。
- 补充已有方案：只填充空缺或缺失的章节。
- 覆盖已有方案：逐项展示新旧对比，经用户确认后覆盖。

新旧章节按来源文件与章节序号对应；来源内容哈希变化时章节划分可能已变，仅允许新建方案。覆盖或补充章纲后，确认界面提示所属卷纲与总纲已过期，并提供“重新汇总本卷与总纲”选项；细纲与章纲同批重提取时细纲不退回。

### 六、素材提取流水线

素材提取与大纲提取是两类独立任务：任务状态分开保存，写入目标分别为 `lorebook/` 与大纲库，界面入口与进度面板分开。两者共用来源切分与 P 编号、后台任务框架（进度、按单元状态与单独重试）、对比确认交互，以及”原文前缀 + 任务目标在末尾”的提示词结构。素材提取类别中不再包含大纲与细纲，首版以 `note` 保存大纲、细纲的行为随之取消。

素材提取同样是纯程序流水线，按固定流程执行；按约五万字分块，因为素材不依赖章节结构。每个分块的每个类别各调用一次模型，逐块逐类串行；同一分块的各类别调用互相独立，各自提示词前缀为该块原文，通过缓存命中减少成本。

#### 提取类别与处理模式

| 类别 | 处理模式 | 保存目录 |
|---|---|---|
| 角色 | 实体型 | `lorebook/character/` |
| 势力 | 实体型 | `lorebook/faction/` |
| 物品 | 实体型 | `lorebook/item/` |
| 地点 | 实体型 | `lorebook/location/` |
| 特殊规则 | 实体型 | `lorebook/system/` |
| 文风 | 文档型 | `lorebook/instruction/` |
| 世界观 | 文档型 | `lorebook/world/` |
| 写作手法 | 文档型 | `lorebook/note/` |
| 素材特点 | 逐条收录 | `lorebook/note/` |

- **实体型**：每个实体一个文件夹，逐块追加新揭示信息到该文件夹，程序按同名或别称聚合至同一文件夹；流水线暂停后用户归类（勾选两个以上文件夹表示它们是同一实体），再调度模型整合；支持用户勾选任意两个以上实体条目交给程序发起合并调用。角色、势力、物品、地点、特殊规则适用。
- **文档型**：每块产出本类一份分析稿，全部块完成后调度模型整合为本类终稿。
- **逐条收录**：素材特点指具体章节或分块中特别的剧情安排或表现形式，绑定位置、没有可合并的名称；每条带所在位置与 P 段落引用，不做同名合并或终稿整合。
- 写作手法偏可迁移的通用技法，素材特点偏落在具体位置的具体安排。两者均允许涉及剧情发展，是对原计划第 6.1 节”素材模板不涉及剧情发展”的例外；其余类别仍遵守该规则。写作手法与素材特点同在 `note/`，以元数据区分类型。
- 所有素材在元数据中标记来源为”用户设计”或”提取”；提取素材另带来源文件、内容哈希与段落引用。无此标记的已有素材视为用户设计。
- 原创设计保持现有八类，不新增写作手法与素材特点：这两类是从作品中学习得来，无法自行设计。参考资料不作为提取类别；原创设计中现有的”写作指导与参考资料”方向不受影响。

#### 详细流程

1. **逐块逐类提取**：程序把一个分块的原文作为提示词前缀，然后对九个类别依次独立调用；每次调用只提取一类，同一分块的各类调用前缀相同、通过缓存命中节省成本。一块的全部类别提取完成，进入下一块。实体型类别调用时，提示词在原文之后、任务之前另附已知实体名单（不破坏原文前缀缓存），模型可输出已有实体的标准名称，程序追加到对应文件夹而非新建，从源头减少别名注册成新实体的情况；该名单只放进实体型调用的上下文，不影响其他类别。

2. **校验与修复重试**：程序按模板校验每次产出，检查字段完整性、P 编号有效性及引用是否在本块范围内。不通过时，把本次产出和错误信息拼到提示词末尾（提示词模板预留”错误信息”位置，平时留空），再次调用。同一”块 × 类别”单元连续失败两次时，程序标记该单元为失败、上报给 Agent 或用户，流水线继续处理其他单元。

3. **中间产物存放**：所有类别的中间产物均存放在 `.nbook/inspiration/extractions/<任务 ID>/` 下：
   - 实体型：每个实体一个文件夹，含各分块对该实体的提取片段；后续分块揭示新信息时追加到同一文件夹。
   - 文档型：每个类别一个文件夹，每块一份分析稿。
   - 逐条收录：每条一个文件，带所在分块与 P 引用。

4. **用户归类（实体型专有）**：全部分块提取完成后，流水线暂停，展示实体文件夹列表供用户归类。程序根据各实体文件中”别称”字段，自动标出疑似同一实体的候选；用户勾选两个以上文件夹表示它们是同一实体，防止别名、昵称注册为新实体。角色、势力、物品、地点、特殊规则均适用此步骤。

5. **模型整合**：
   - 实体型：对每个实体（或用户归类后的实体组），模型读取文件夹内全部文件，去重整合为该实体终稿。
   - 文档型：对每个类别，模型读取文件夹内全部分块分析稿，整合为本类终稿。
   - 逐条收录：不做整合。

6. **角色特殊处理**：角色主文件只放基本人设（外貌、性格、能力等），不涉及剧情；角色文件夹下另建子文件夹存放经历与人际关系。经历按分块顺序整理成时间线，保留各段 P 引用；人际关系也按时间顺序记录，均不做去重合并。物品、势力、地点按原计划模板不涉及剧情，无此子文件夹。

7. **新增模板**：以下字段均非必填，无对应信息留空；“参考片段”统一用 P 编号引用原文，由程序还原。

   | 模板 | 字段 |
   |---|---|
   | 写作手法 | 手法名称、类型（叙事 / 描写 / 对话 / 结构 / 节奏等）、手法说明、适用场景、实现要点、效果、参考片段 |
   | 素材特点 | 名称、所在位置（分块与章节）、类型（剧情安排 / 表现形式）、安排描述、效果、参考片段 |
   | 角色经历 | 时间顺序（分块与章节）、阶段名称、经历描述、对角色的影响、参考片段 |
   | 角色人际关系 | 关联角色、关系类型、关系描述、变化节点（分块与章节及变化内容）、参考片段 |

8. **审阅与写入（方案 C）**：
   - 整合完成后，用户在审阅清单批量确认，可编辑、删除、拆分误合并或勾选几条手动合并，新条目默认全选，一次性批量写入 `lorebook/` 对应目录。
   - 和已有素材同名时进入对比确认，可选覆盖、另存或跳过。
   - 中间产物一直保留至用户手动清理，或重新提取时被覆盖，支持拆分误合并与只重提某几块。
   - Agent 可代用户批量确认新条目写入；与用户设计条目冲突的覆盖必须由用户本人确认。

### 七、提取模型的调用参数

大纲提取（细纲、章纲）与素材提取的模型调用一律关闭思考，由流水线固定设置，不受工作台思考开关影响；输出质量由模板校验与修复重试保证。

## 数据、接口、安全、迁移、发布与回滚影响

- 大纲 manifest 的总纲表示从全局 `totalId` 改为按方案确定；需要定义新 schema 版本及旧文件读取归一规则，旧数据按“所有方案共享同一总纲”解读，不改写用户文件。回滚需保证新格式文件在旧版本中被明确拒绝而非误读。
- 细纲采用依据新增“来源提取”类型，写作交接需识别该依据。
- 新增后台提取任务的持久化状态（任务、逐章状态、来源哈希、划卷结果），需定义存放位置与项目关闭、重开后的恢复语义。
- 素材提取中间产物存于 `.nbook/inspiration/extractions/<任务 ID>/`，属于项目内部状态，不进入 `lorebook/`；需定义目录结构、清理入口与重提覆盖语义。实体文件夹内的子文件夹能否作为 lorebook 内容节点正常索引，实施前需核实内容节点结构。
- 素材元数据新增来源标记字段；缺失时视为用户设计，旧素材无需迁移。
- 来源作品保持只读；所有大纲写入经大纲领域操作与工作区历史，所有素材写入经现有 tracked workspace writes，不建立旁路写入。
- 真实模型调用、数据库迁移与发布仍需各自授权。

## 对 Spec 的预期改动

- `outline.planning-library`：总纲改为每方案一个、手动关联共享；修订“不提供导入”条款，登记提取方案；细纲新增来源提取采用依据及其豁免规则。
- `outline.writer-handoff`：按方案读取总纲；识别来源提取细纲的可写资格。
- `inspiration.workbench`：章节识别与修正、划卷、流水线进度与重试、数据去向选择与对比确认；首版“大纲、细纲以 note 保存”的行为被替代。
- 新增大纲提取流水线 capability：任务状态、取消、失败恢复、缓存友好的提示词结构、各工作流输入输出与验收。
- 新增素材提取流水线 capability：九类类别与三种处理模式、逐块逐类调度与缓存结构、模板校验与修复重试、上报条件、中间产物目录、归类暂停点与疑似候选、整合规则、角色经历与人际关系子文件夹、写作手法 / 素材特点 / 角色经历 / 角色人际关系模板、审阅清单与冲突确认、来源标记元数据、写作手法与素材特点在 `note/` 内的类型区分。
- 两条流水线的提取调用固定关闭思考，不受工作台思考开关影响。
