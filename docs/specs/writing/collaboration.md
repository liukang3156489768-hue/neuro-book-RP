# 助手与作家系统

## 目标与非目标

写手原生酒馆预设的绑定、编译记录与恢复边界见 [写手兼容](tavern-preset-compatibility.md)；其目标不改变本能力的资料审核与正文写入职责。

本能力把一章细纲写成正文，或按用户要求改写正文中的一段。主创对接用户，资料助手按细纲读取资料并补充提示，独立审核助手核验补充稿，写手只按通过审核的提示写作。循环由程序推进，按场景逐段写作与审阅；每个场景都带着已通过的正文写作，保证全章连贯。

### 保留规划重写与正文删改（2026-10-10）

- 用户明确要求从头重写正文时，`start_writing(task="rewrite")` 默认复用该章最近的已确认场景规划，从场景 1 重新写作与审阅，已写场景数重置为零。不会先清空旧正文；第一个新场景通过后才替换旧正文，后续场景逐段追加，旧版本保留在文件历史中。
- 复用前仍读取当前细纲、规划依据、文风和资料。依据或已确认规划的资料来源变化、旧规划缺新版资料结构时，从头重新补充并审核；规划只有部分已确认时，保留有效前缀并规划剩余场景。用户明确要求重新规划时传 `reusePlan=false`。不修改大纲库或原细纲。
- 用户要求删除正文或直接采用用户提供的替换文案时，主创先用 `read_chapter_prose` 获取正文全文版本哈希和段号，确认范围与文案后调用 `edit_chapter_prose`。目标可为段号或唯一原话，扩展到完整段落；无目标表示全章，替换文案为空表示删除。
- 删改仅修改正文内容，保留正文文件、章节关联、其他文件头字段和已确认场景规划，清除不再有效的旧生成依据。通过项目变更边界记录历史。没有正文文件或归属冲突时拒绝；读后版本发生变化时返回未修改，主创重新读取并确认。
- 正文删改与生成共用章节锁：有运行中、等待确认或中断未关闭的任务时不能直接删改。主创不能通过该工具自行创作正文，模型润色继续用局部改写流程，重新生成整章正文使用整章重写流程。
- 提示与阻断问题均可由用户忽略；已忽略条目再次被助手提交时不阻断写作。忽略不豁免输入可读性、结构解析和写入版本检查，详见 [问题回流](issue-feedback.md)。

验收：完成一章后保留规划重写，助手规划及资料审核调用不重复，写手从场景 1 重新产出；修改细纲后重写会重新规划审核。删除第二段只移除该段，全章清空仍保留文件与规划，过期正文哈希不能覆盖新内容。

### 资料补充与独立审核（2026-10-04）

批准依据：[细纲资料补充与独立审核](../../proposals/writing-detail-material-review.md)。

- 原细纲新增可选的场景地点、角色服饰与外观状态；参与角色可带缩进的资料引用、当前状态与外貌要求。程序保留作者字段，不接受助手改写情节。
- 助手按姓名或明确引用读取已有角色目录，补充各参与角色的身份、外貌、性格及具体表现；按情节筛选环境、关系、经历、秘密与信息差、服饰物品和写法。笔记先索引后对应文档，不能把未来方案计划当作当前事实。
- 补充稿具有分类、对象、要点与来源摘录定位，程序校验来源和参与角色覆盖。关键资料缺失不允许编造；补充稿与原细纲分层发送，不写回原文件。
- 写手调用前，独立审核 Profile 在独立会话对照原细纲、补充稿、相关前文与来源核验充分性、事实、连续性、方案及认知边界。审核仅返回通过或具体问题，不改稿。资料助手修订后重新审核，最多退回三次；非法审核提交最多重交三次，耗尽明确停止，无正文写入。
- 讨论模式保留每个场景的主创核对与用户确认；自动模式由独立审核助手通过后自动推进。两种模式均保留正文产出后的审阅。局部改写也审核资料稿，保持用户修改范围及最终替换确认。
- 新流程使用新 workflow 身份；历史记录只读展示。旧停止运行的检查点没有新版补充资料时，续写须重新补充和审核未写部分，已通过正文仍按细纲原文核对。
- 所有新增提示词进入全局提示词管理；审核采用助手的模型配置但独立 Profile、会话和提示词。

### 角色目录的按需读取（2026-10-10）

角色文件结构遵循 [角色管理工作区](../ui/character-management.md)。资料助手与独立审核使用相同的身份、方案及认知边界：

- 基础人设来自 `lorebook/character/<character-id>/index.md`：`id` 是稳定身份，`title/aliases` 是姓名和别名；`ext.character.profile` 提供身份、外貌、常规穿着、家庭、经济、能力、性格及具体表现。明确引用优先，否则通过姓名或别名解析入口，再用稳定 ID 读取侧面文件；重名或关键资料缺失登记问题，不任意选取角色。
- `original/experience.md`、`original/relationships.md`、`original/knowledge/index.md`、`original/state.md` 分别表示原作经历、人际关系、已知事件信息和原作侧面的状态。`plans/<plan-id>/` 下相同结构属于一个特定大纲方案；当前方案身份来自调用输入 `planId`，局部改写来自 `guidance.planId`。当前方案缺失资料不自动回退原作或其他方案；原作仅作为细纲明确引用或比照的参考。
- 经历、关系及知识记录以 YAML `records` 表示，`title/content/source` 表示条目内容与来源，`targetId` 表示关系对象，`unknown/misunderstanding` 表示信息差及误解。状态来自 `state.chapter/location/items/psychology`，是最近正文快照，读取时核实其时间位置，不将较晚章节状态用于较早场景。未来计划不视为已发生经历或角色已知信息。
- `read_writing_material` 对角色文件额外返回基础人设、记录与状态的结构化字段，其他文件仍只返回正文。角色结构化资料不包含整份提取来源清单，不参与正文段号；正文标题、段号和摘录校验保持现有口径。非法角色文件头明确报错，不静默丢失人设。
- 提取时不预填知识，正文状态初始为空。缺失文件、空数组或空字段表示尚未记录，不推断角色确定知道或不知道，也不要求模型填满。只补充本场景需要的信息，必要事实不足或来源冲突才阻断。
- 写手继续使用原细纲加 `supplements`。参与角色各有一项 `character`，姓名与细纲保持一致；其他关系、经历、认知差异与服饰按现有类别补充，标明原作参考和当前方案事实，附真实文件正文摘录定位。结构化事实可以提炼为要点，但不得伪造 YAML 的正文标题或段号。助手不写回原细纲或角色文件。

本能力不做剧情决定，不修改大纲规划，不读取伏笔定义，不沿用现有 `writer` Profile 的设置。

## 术语与参与者

- **主创**：用户在写作会话里对话的角色。确认写哪一章、改哪一段、怎么改；发起写作或改写；核对场景规划；向用户报告问题和结果。
- **助手**：由程序调用的角色。读取细纲与资料，填写场景规划和改写提示中需要判断的字段，审阅写手的产出。
- **独立审核助手**：使用独立会话核验原细纲、资料补充稿与来源，只有明确通过后才交写手；默认沿用助手模型配置，提示词单独管理。
- **写手**：由程序调用的角色。每次调用都是全新的上下文，只看到文风和模板渲染后的提示，只输出正文。
- **写作工作流**：推进场景循环的程序。渲染提示、调用写手与助手、校验提交、写入正文、记录运行过程。
- **场景**：细纲“章节细纲”下的一个 `## 场景N` 小节，是写作和审阅的最小单位。场景只存在于写作过程中，不出现在成品正文里。
- **场景规划**（结构 A）、**场景写作提示**（结构 B）、**审阅结果**（结构 C）、**改写提示**（结构 D）：四份固定结构，定义见下文。
- **已通过正文**：本章中已经审阅通过并写入正文文件的内容。

## 输入与前置条件

- 章节状态可写（见 [writing.prose-binding](prose-binding.md)），并且作品写作设置里已选择文风文件。没有文风文件时，主创提示用户先设置，不开始写作。
- 规划上下文只来自规划只读交接（[outline.writer-handoff](../outline/writer-handoff.md)）：写作方案中的正式章节大纲、已审阅细纲、写作指导、参考清单和伏笔标记原文。线路规划暂时只供用户梳理剧情，不作为写作输入。
- 主创从用户对话中得到任务类型：新写一章、续写（从第一个未通过的场景继续）、整章重写或局部改写。整章重写只在用户明确要求时发起，发起前主创告知用户现有正文将被替换，旧正文保留在历史中。

### 角色权限

| 角色 | 能读取 | 能提交 | 不能做 |
|---|---|---|---|
| 主创 | 章节状态、场景规划、审阅结果、运行进度、正文文件 | 调度写作与重写；核对场景规划；向用户提问；通过限域工具执行用户确认的正文删改 | 读取原始资料；通用文件写入；自行创作正文 |
| 助手 | 交接内容；`lorebook/`、参考资料目录、`lorebook/instruction/` 只读 | 场景规划、改写提示中归助手的字段、审阅结果、问题登记 | 读取伏笔定义；写任何文件 |
| 独立审核助手 | 原细纲、资料补充稿、相关前文；与资料助手相同范围的来源文件 | 资料审核通过或具体退回问题 | 改稿、规划剧情、生成正文、读取伏笔定义、写任何文件 |
| 写手 | 仅渲染好的提示 | 正文文本 | 使用任何工具 |

文件写入全部由写作工作流完成。

## 输出与可观察行为

### 场景切分

细纲模板见 [outline-entry-templates.md](../outline/outline-entry-templates.md) 的“细纲”一节，细纲的写作信息全部写在正文里。

- 一章只用一份细纲：总览描述整章，多份细纲的总览与禁止事项无法合并。本章有多份细纲时写作不开始，登记阻断问题“细纲结构不完整”，提示合并为一份。
- 细纲“章节细纲”下的每个 `## 场景N` 或 `## 场景N：名称` 是一个场景，编号从 1 连续；“章节总览”与“禁止事项”不是场景。
- 场景的字段（场景简述、字数要求、人称要求、情绪基调、剧情节奏）与小节（场景地点、参与角色、角色服饰与外观状态、具体情节、描写、写作指导、参考资料、伏笔）都从正文读取。地点、服饰及角色缩进字段是新增的可选内容，缺少这些字段不使既有第三版细纲失效。
- 细纲不满足细纲结构检查（见模板文档的约束规则）时，场景规划失败，登记阻断问题“细纲结构不完整”，并说明需要修改的地方。正式采用的细纲已经过这项检查；旧模板的细纲不兼容，需要重新生成。

### 字段分工

凡是能从源文件直接得到的内容都由程序截取填入，助手只填需要判断的字段。

| 字段 | 填写方 | 来源 |
|---|---|---|
| 章节总览 | 程序 | 细纲“章节总览”的章节标题、剧情概括、核心冲突、情绪基调、目标字数 |
| 场景一览 | 程序 | 本章全部场景的名称、字数和结尾落点，标出当前场景；另列上一场景的结尾落点，以及下一场景的名称与场景简述（只供结尾铺垫） |
| 本场景字段 | 程序 | 场景简述、人称、目标字数、情绪基调、剧情节奏 |
| 参与角色、具体情节、描写、写作指导 | 程序 | 场景对应小节原文 |
| 场景地点、角色服饰与外观状态 | 程序 | 新增小节原文；角色资料引用、当前状态与外貌要求保留在参与角色中 |
| 本章写作指导 | 程序 | 章节大纲的 `writingGuidance` 原文 |
| 本章伏笔标记原文 | 程序 | 章节大纲中伏笔标记处的原文和动作（埋设、强化、回收），按出现顺序排列，附进每个场景；分配给本场景的标出“本场景执行”，其余标出“不在本场景执行”；不含伏笔定义，也不按线路判断伏笔先后 |
| 本场景伏笔 | 程序 | 场景“伏笔”小节认领的标记：原文、状态与效果；作用只交给助手审阅，不进写手提示 |
| 禁止事项 | 程序 | 细纲“禁止事项”，每个场景都带上 |
| 上一章结尾 | 程序 | 上一章正文文件末尾约 1500 字，按段落边界截断，只放进场景 1 |
| 已通过正文 | 程序 | 正文文件的当前内容 |
| 文风 | 程序 | 解析当前文风文件 |
| 写作手法补充 | 助手 | 只在确有需要时从写作指导类素材中补充要点或摘录，不复述细纲的写作指导 |
| 背景知识 | 助手 | 从参考资料中提炼“需要知道什么”：要点，或截取的重要段落；优先使用场景的参考资料 |
| 按需资料补充（`supplements`） | 助手 + 程序 | 助手提交分类、对象、要点及来源定位，程序解析来源摘录；每个参与角色恰好一项基础资料，其他环境、关系、经历、秘密、服饰、物品与参考按情节提供 |
| 必须写到的要素 | 程序 + 助手 | 依次为：具体情节逐条、本场景执行的伏笔；助手只能在其后追加 |

- **截取段落**：助手只提交“文件路径 + 标题或段落位置”，由程序取出原文填入。单段摘录不超过 1000 字，每个场景的摘录合计不超过 3000 字，超出时提交被拒绝。
- **上一章**：写作方案中按大纲库层级顺序（见 [writing.prose-binding](prose-binding.md)）排在本章之前、最近一个有正文的章节，可以跨卷。没有上一章正文时，场景 1 不带结尾片段，并登记提示问题“上一章尚无正文”。

### 结构 A：场景规划

助手按细纲顺序每次只提交一个场景。输入包含章节总览、整章场景边界摘要、此前已确认场景的摘要、当前场景从细纲读出的字段与小节、禁止事项及本章参考文件清单；此前场景的完整补充稿不重复附入。当前场景未通过时，不能开始下一个场景的规划。提交包含：

- 章节依据：写作方案、章节大纲与本章细纲的 id、版本和内容哈希，以及细纲总览的目标字数，由程序填写。
- 当前场景：`scenes` 数组恰好一项，包含场景编号、对应的场景标题、写作手法补充、背景知识、按需资料补充（`supplements`）、追加的必须写到的要素（可以为空）。效果要求就是细纲的场景简述，助手不填。
- 发现的问题：按 [writing.issue-feedback](issue-feedback.md) 登记。

程序校验项：只提交当前场景，编号与标题和细纲对应，参与角色基础资料覆盖且没有多余或重复角色，明确角色引用包含在对应来源中，来源可读、摘录位置有效，包含补充资料在内的摘录长度在限制内。校验失败的提交退回助手，并附上失败原因；它不会交到主创和写手手中。通过后先由独立审核助手核验当前场景。

独立审核结果为 `{passed, problems}`：通过时问题列表为空，退回时必须列出具体问题。每份修订稿新建独立审核会话，不继承资料助手的聊天。有效退回最多三次，非法结果最多重交三次，耗尽即停止。来源内容哈希随通过程序校验的稿件记录；写手调用前及正文写入前核对，资料已变化或不可读时停止，续写重新补充和审核。

讨论模式下，主创核对当前场景内容是否合理，例如追加的要素是否偏离场景简述、是否把剧情写偏；通过后交用户确认。退回时附意见，只重做当前场景，已确认场景不重复规划。主创与用户对同一场景合计退回满 3 次即停止并报告。自动模式下，独立审核通过即确认当前场景，不创建主创或用户待应答项，自动继续下一场景的规划。

每确认一个场景就保存检查点。整章全部场景规划确认完成后，才进入逐场景正文写作循环；规划阶段不生成或写入场景正文。程序校验失败与独立资料审核退回的上限也分别按当前场景计数，均为 3 次。

### 结构 B：场景写作提示

写作工作流按所选提示词预设渲染。内置默认把写作内容拆成逐条独立条目（见 [全局提示词管理](../ui/prompt-management.md)），每条可在提示词管理中单独排序、启用停用和改角色；按内置顺序，写作内容依次为：

1. 系统部分：写手职责（固定文本）、文风要求、禁用写法、样文，各为独立条目。
2. 上一章结尾。
3. 章节总览与场景一览。
4. 已通过正文。
5. 本章写作指导。
6. 本章伏笔标记原文（标出本场景执行的）；本场景的场景简述、人称、目标字数、情绪基调、剧情节奏，场景地点、参与角色、角色服饰与外观状态、具体情节、描写、写作指导，本场景伏笔的原文、状态与效果。
7. 通过独立审核的按需资料补充、写作手法补充、背景知识、必须写到的要素、不能出现的情节（禁止事项）。
8. 上次审阅的问题清单。
9. 输出要求：只输出本场景正文，与已通过正文直接衔接，不加标题、分隔符或说明；只写到本场景结尾落点，严禁提前展开下一场景的剧情；允许在结尾铺垫下一场景，使下一场景能顺畅接入，但不写出下一场景的具体事件和冲突；执行伏笔时只写到标记原文的程度，不提前揭示。

第 2 项和第 8 项是条件性小节，改为统一占位：变量始终存在，不适用时渲染占位文案（非场景 1 的“上一章结尾”写“不提供”，非重写的“上次审阅的问题清单”写“无”），而不是整段消失。这样它们和其余小节一样是可排序、可停用的普通条目；非场景 1 的写手提示也会带“上一章结尾”标题，内容是占位说明。

自定义预设继续保留设定的消息顺序和角色。事实性小节（上一章结尾、章节总览、场景一览、已通过正文、写作指导、伏笔标记、场景各字段、必须写到的要素、禁止事项、资料补充等）承载的变量是必需变量，停用会使其缺失，保存时被服务端拒绝；文风文件的“禁用写法”“样文”本身允许留空，是仅有的两个可停用小节。正文审阅接收写手本次实际采用的提示词版本与结构。

### 结构 C：审阅结果

写手产出后，写作工作流把结构 B、写手的产出，以及本场景伏笔的原文、状态、作用与效果交给助手审阅，并统计字数。助手提交：

- 是否通过；产出写出了下一场景的具体事件、冲突，或推进了下一场景的情节时判定不通过，结尾的铺垫与过渡不算越界；
- 逐项列出“必须写到的要素”是否已写到；伏笔要素同时检查达到了效果、没有点明作用、没有超出标记原文提前揭示；
- 逐项列出“不能出现的情节”（禁止事项）是否出现；
- 问题清单：不通过时必填，会附进重写提示。

同时满足以下条件才算通过：助手判定通过，要素全部写到，禁止事项全部未出现，字数达到目标的 70%。

### 场景循环

1. 按场景顺序，从第一个未通过的场景开始。
2. 渲染结构 B，调用写手。
3. 调用助手审阅，得到结构 C。
4. 通过：把本场景正文追加到正文文件末尾，与前文以段落分隔，然后进入下一场景。
5. 不通过：把问题清单附进结构 B，重写同一场景，最多重写 2 次。仍不通过时停止，场景标为“未通过”，由主创向用户报告，等用户决定。
6. 全部场景通过后，写入正文依据（见 [writing.prose-binding](prose-binding.md)），统计整章字数；整章字数不足细纲总览目标字数的 70% 时，主创在报告中说明，不触发重写。

每个场景开始前，写作工作流重新读取交接结果。章节大纲或细纲的版本已与场景规划记录的不一致，或章节已不可写时，写作停止，并登记阻断问题“规划已在写作中变化”。

### 结构 D：改写提示

1. 用户在正文编辑器中选中文字，或在对话中描述要改的位置，由主创定位。目标范围扩展到选区所在的完整段落。
2. 程序截取目标段落，以及上文和下文各两个完整段落；章首或章末不足两段时有多少取多少。
3. 助手填写修改要求（依据主创整理的用户要求）、写作手法、背景知识、人称及所需的资料补充；程序校验通过后由独立审核助手对照原细纲、用户要求、目标段落及上下文审核，通过才调用写手。
4. 写手看到的内容依次为（与结构 B 同一拆分口径，每条独立可排序/停用/改角色）：
   - 系统部分，同结构 B；
   - 上文两段、目标段落、下文两段；
   - 修改要求、人称、写作手法、背景知识、通过审核的资料补充；
   - 上次审阅的问题清单，同结构 B 的统一占位处理；
   - 输出要求：只输出替换目标段落的新正文。
5. 助手审阅改写结果是否满足修改要求，不通过时最多重写 2 次。
6. 用户在会话中看到新旧对照，确认后由程序替换目标段落，放弃则不改动。确认时目标段落或补充资料来源已被改动的，不替换，提示用户重新发起。

### 文风文件

- `lorebook/instruction/` 下 `type: instruction`、`subtype: writing-style` 的文件都可以作为文风文件，建议放在 `lorebook/instruction/writing-style/` 下。
- 正文按二级标题解析：
  - `## 文风要求`：必填且非空；
  - `## 禁用写法`：可为空；
  - `## 样文`：可为空；
  - 其他小节忽略。
- 解析结果原样填进写手系统部分的对应位置。缺少“文风要求”时写作不能开始，并提示具体原因。

### 字数口径

统计正文中的非空白字符，包括标点，不计 Markdown 标记符号。场景只要达到目标字数的 70% 即通过，不限上限；整章字数不足细纲总览目标字数的 70% 时登记提示。各场景字数要求之和与整章目标相差超过 50% 时登记提示。

### 助手模式

助手的系统提示按任务类型分片按需加载：

- **场景规划模式**（plan-scenes）：读取章节总览、整章场景边界与已确认摘要、当前场景字段与小节、伏笔标记原文，只填写当前场景规划（结构 A）中归助手的字段。
- **场景审阅模式**（review-scene）：接收写手提示和写手产出，提交审阅结果（结构 C）。
- **改写规划模式**（plan-rewrite）：读取用户修改要求、目标段落及上下文，填写改写提示（结构 D）中归助手的字段。
- **改写审阅模式**（review-rewrite）：接收改写提示和写手产出，判断是否满足修改要求。

助手会话在场景规划后保持，审阅每个场景时复用；每次调用的 payload 中带 `kind` 字段指明当前模式。基础职责与问题登记规则在所有模式中共享；具体规则按 `kind` 加载对应模式的提示片段。

### 整章写作模式（预留）

当前实现是逐场景写作：助手为每个场景单独规划，写手一次写一个场景，场景通过后追加到正文末尾。

预留整章写作模式：助手为整章规划一次，写手一次性完成整章正文，助手审阅整章产出。该模式的合同（plan-chapter、review-chapter）已在助手提示中预留，但工作流暂未实现；写作粒度由用户在发起时选择，当前只提供场景模式。

## 状态与转换

| 当前 | 事件 | 下一状态 |
|---|---|---|
| 空闲 | 主创发起写作 | 规划中 |
| 规划中 | 程序校验失败 | 规划中（退回助手） |
| 规划中 | 程序校验通过 | 资料审核中 |
| 资料审核中 | 审核通过，讨论模式 | 规划中（交主创核对，再交用户确认） |
| 资料审核中 | 审核通过，自动模式 | 保存当前场景；还有未规划场景则继续规划，否则写作中 |
| 资料审核中 | 审核退回，未满 3 次 | 规划中（修订后重新独立审核） |
| 资料审核中 | 审核退回满 3 次或非法提交耗尽 | 已停止 |
| 规划中 | 主创退回，未满 3 次 | 规划中 |
| 规划中 | 登记了未忽略的阻断问题，或主创退回满 3 次 | 已停止 |
| 规划中 | 讨论模式主创核对与用户确认通过 | 保存当前场景；还有未规划场景则继续规划，否则写作中 |
| 写作中 | 场景通过且还有场景 | 写作中（下一场景） |
| 写作中 | 场景重写 2 次仍不通过 | 已停止（场景未通过） |
| 写作中 | 规划在写作中变化 | 已停止 |
| 写作中 | 用户停止 | 已停止 |
| 写作中 | 全部场景通过 | 已完成 |
| 已停止 | 用户续写，依据与来源未变且检查点含新版资料 | 沿用已确认规划；有未规划场景先规划，否则从第一个未通过正文审阅的场景写作 |
| 已停止 | 用户续写，依据或来源已变，或检查点缺新版资料 | 规划中（重新补充和审核） |

- 同一章同时只能有一次写作或改写在运行；运行中再次发起会被拒绝，并提示当前进度。
- 续写时，已通过正文取正文文件的当前内容，包括用户在停止期间的手改。
- 每一步都记入写作运行记录：渲染后的提示、写手产出、审阅结果、校验失败原因。进程中断后按运行记录恢复，已完成的步骤不重复执行。

## 副作用与数据

- 写作运行记录保存在 Project 内，按章节可查。
- 正文文件的追加、段落替换和依据写入都走项目的文件写入与历史快照。
- 运行期间，本章正文文件在写作界面中只读（见 [writing.workspace-ui](workspace-ui.md)）。
- 调用主创、资料助手、独立审核助手、写手四个角色，产生模型调用费用；审核默认沿用资料助手的模型设置。

## 失败与恢复

- 模型调用失败或超时：当前步骤按运行记录重试一次，仍失败则停止，已通过的场景保留。
- 写手输出为空：视为审阅不通过。
- 写入正文文件失败：停止，本场景不算通过，续写时重做本场景。
- 用户停止：取消正在进行的调用；迟到的结果不写入运行记录，也不写入正文。
- 文风文件、参考文件在运行中被删除或改为不可读：停止，并登记阻断问题。

## 边界与兼容

- 只通过规划只读交接读取规划，不写入规划或伏笔；`lorebook/` 只在用户从写作设置新增或删除文风时由程序写入（见 [writing.prose-binding](prose-binding.md)），模型不写。
- 资料助手与独立审核助手不能读取伏笔定义，写手没有任何工具，四个角色都没有写文件的能力。
- 与现有 `writer` Profile、Plot、Writer Brief 和 World Engine 互不依赖。
- 结构 A 到 D 和文风文件格式是本模块的公开合同，变更时需要同步更新本规范。

## 验收与 Smoke

- Given 本章有两份细纲，When 发起写作，Then 写作不开始，登记“细纲结构不完整”阻断问题，提示合并为一份。
- Given 章节大纲中有一处伏笔埋设标记并分给场景 2，Then 每个场景的写手提示都含该标记处原文和动作，场景 2 标为本场景执行、其他场景标为不在本场景执行，不含伏笔定义。
- Given 细纲有章节总览和三个场景，When 发起写作，Then 场景规划有 3 个场景，每个场景的写手提示都含章节总览各字段和列出 3 个场景的场景一览，并标出当前场景。
- Given 讨论模式有多个场景，Then 每次助手只提交当前一项规划；当前场景主创核对与用户确认均通过后才规划下一项，全部确认前写手调用数为零。
- Given 第二个场景被退回，Then 只修订第二个场景，第一项已确认规划不重做；停止后续写也保留第一项。
- Given 自动模式，Then 每项规划经程序校验与独立审核模型通过后自动推进，审核退回只重做当前场景，整章规划流程无人工待应答项。
- Given 某场景缺字数要求、人称要求、场景简述或具体情节，When 发起写作，Then 写作不开始，登记“细纲结构不完整”阻断问题。
- Given 场景有两条具体情节、认领一个伏笔，Then 必须写到的要素依次是这两条情节和该伏笔，助手的追加项排在其后；最后一条情节是结尾落点。
- Given 细纲有禁止事项，Then 每个场景的写手提示含“不能出现的情节”；审阅判定某项出现时本场景不通过。
- Given 场景认领了伏笔，Then 写手提示含该伏笔的原文、状态与效果，不含作用；审阅输入含作用。
- Given 场景规划，Then 写手提示里的具体情节、描写与写作指导与细纲源文件对应小节一致；下一场景只给名称和场景简述。
- Given 助手提交的摘录位置在文件中不存在，Then 提交被程序拒绝并退回助手，写手未被调用。
- Given 场景 1 通过，When 写场景 2，Then 写手提示包含场景 1 的正文，且正文文件末尾已追加场景 1 的正文，没有标题或分隔符。
- Given 某场景审阅两次重写后仍不通过，Then 写作停止，正文只含此前通过的场景，主创向用户报告问题清单。
- Given 写作中途用户停止，When 再次发起写作，Then 从第一个未通过的场景继续，已通过场景不重写。
- Given 写作中细纲被修改，When 下一个场景开始，Then 写作停止并登记“规划已在写作中变化”。
- Given 用户选中一句话要求改写，Then 目标扩展到整段，写手提示含上下各两段，用户确认前正文不变，确认后只替换目标段落。
- Given 文风文件缺少“文风要求”，Then 写作不能开始，并提示原因。
- Given 助手尝试读取伏笔定义文件，Then 读取被拒绝。
- Given 进程在第 2 个场景审阅时中断，When 恢复，Then 从第 2 个场景的审阅步骤继续，不重复调用写手。

Smoke：用按新模板写的、含三个场景的示例细纲完成一章写作，检查正文文件内容连续、文件头 `source` 正确、运行记录中每个场景的提示和审阅结果完整；再对其中一段发起改写，确认对照与替换行为。

### 角色 Profile 与工具

- 主创 `writing.lead`：
  - 初始值 `{chapterEntryId?}`，项目取会话绑定的当前 Project；写作视图按章创建的会话绑定章节，提示据此把它作为默认章节，工具仍按参数中的章节执行；
  - 工具：`get_writing_status`、`start_writing`、`continue_writing`、`stop_writing`、`answer_scene_plan`、`start_rewrite`、`answer_rewrite`、`read_chapter_prose`、`request_user_input`，不含任何文件读写与资料读取工具；
  - `read_chapter_prose` 与助手读取资料同样按段标注段号，`start_rewrite` 的段号目标与之同一口径；
  - 发起、续写、改写、应答标记为工作区变更，会话处于只读模式（discuss、plan）时由 harness 先请用户批准；
  - 核对与讨论模式的用户确认都经 `answer_scene_plan` 应答。两者按待应答项标题区分，“确认场景规划”只能转交用户本人的决定，这一点对主创由提示约束；界面应答时程序拒绝用户应答主创核对；
  - 改写确认（标题“确认替换改写段落”）只能经 `answer_rewrite` 应答，`answer_scene_plan` 拒绝它；同样只能转交用户本人的决定，由提示约束。
- 发起、续写、改写、应答之后，运行在后台任务（`jobs.spawn`，kind `workflow`）中推进：
  - 运行停在等待应答、完成或停止时，报告以后续消息交回主创；用户在界面上续写或应答时，报告交回本章的写作会话，开头写明用户的操作；
  - 一段后台任务只跟踪到下一次停下，应答后开始新的一段；
  - 停止的运行按任务取消结束，失败的运行按任务失败结束，提示可续写；
  - 任务 ref 为 `{writingRunId, chapterEntryId}`，不用 `runId`、`workflowKey`，这两个字段会被演示工作流的待应答面板接管。
- 助手 `writing.assistant`：
  - 初始值 `{chapterEntryId}`，由工作流创建会话时绑定；
  - 工具：`list_writing_materials`、`read_writing_material`、`report_result`；
  - 可读范围按会话绑定章节的当前交接计算（`lorebook/` 与本章参考文件，排除伏笔定义），不接受模型传入章节或路径范围；
  - 读取结果去掉文件头，每段标注段号，与摘录的段落定位同一口径；
  - `report_result` 的 `data` 必填且必须符合输出外壳（`dataSchemaFromInitial`）：模型把 JSON 写进 `result` 字符串时在工具层即被拒绝，而不是交给工作流按规划不合法计次；
  - 调用输入按 `kind`（`plan-scenes`、`review-scene`、`plan-rewrite`、`review-rewrite`）区分；输出外壳只检查 `plan`、`review`、`rewrite` 或 `rewriteReview` 字段，结构 A、C、D 的严格校验与退回由工作流完成；
  - 系统提示由通用部分（职责与资料边界）、本次 `kind` 对应的模式片段、问题登记与退回规则组成；每次调用按 payload 重新渲染，同一会话在规划与审阅之间切换时只看到当前模式；
  - `plan-chapter`、`review-chapter` 是整章编写模式的预留种类，Profile 已有模式片段，工作流尚未发起；
  - 提示只让助手登记 `GUIDANCE_CONFLICT` 与 `OTHER`，其余问题代码由程序登记。
- 写手 `writing.writer`：
  - 初始值 `{system}`，是工作流渲染的结构 B 系统部分，Profile 原样作为系统提示，不追加内容；
  - 无工具，用户提示作为调用消息，最终回复即正文。
- 助手与写手的 Profile 可公开创建：`system_only` 会拒绝工作流经 harness 创建会话。
- 工具经动态导入加载写作领域模块：工具注册表位于 `project-history → config → harness` 的加载链上，静态导入受跟踪写入会成环。

### 写作工作流

- 角色 Profile 键：`writing.lead`、`writing.assistant`、`writing.writer`。
  - 助手：每次运行一个临时会话，场景规划与各场景审阅共用；
  - 写手：每次调用都是新的临时会话，只收到渲染好的结构 B；
  - 场景审阅的调用输入另带本场景伏笔的原文、状态、作用与效果，作用不进写手提示。
- 助手的提交放在结构化结果中：
  - 规划为 `{plan, issues?}`，审阅为 `{review, issues?}`；
  - `issues` 是问题草稿，位置只能指向本章章节大纲或其细纲，不合法时连同结构校验原因一起退回；
  - 每个场景的规划累计 3 次未通过程序校验即停止（`plan-invalid`），审阅结果连续 3 次形状不合法同样停止（`review-invalid`）。
- 核对：
  - 当前场景程序校验与独立资料审核通过后，讨论模式经待应答项（`approve`）交主创核对，再交用户确认；自动模式直接采用独立审核结果，无人工待应答；
  - 应答为布尔值，或 `{approved, comments}`，退回意见交回助手；
  - 主创和用户对同一场景的退回合计满 3 次停止（`plan-rejected`），下一场景重新计数。
- 场景循环：
  - 每个场景开始前重新读取交接，依据版本变化即停止，登记 `PLANNING_CHANGED`；文风或摘录来源不可读即停止，登记 `SOURCE_UNREADABLE`；
  - 通过的场景按正文当前内容的哈希追加，整章重写时第一个场景替换旧正文；正文期间被改动时不覆盖，停止（`prose-changed`）；
  - 正文每次写入都去掉文件头 `source`，全部场景通过后重新写入。
- 检查点：准备完成、每个场景规划确认后、每个场景正文通过并写入后保存 `{plan, passed, replaceBody}`。`plan.scenes` 是已确认规划的连续前缀，`passed` 是已写入正文的数量，两者不能混为同一进度。
- 写作粒度：运行参数 `granularity` 缺省为 `scene`，即本节的逐场景流程。`chapter`（整章编写：助手一次规划、写手一次写成整章、助手整章审阅）为预留位置，尚未实现，收到时运行按 `unsupported` 停止；主创工具目前不传这个参数。
- 首章没有上一章，不登记 `MISSING_PREVIOUS_CHAPTER`。
- 运行结果记录结束方式与原因、已通过和总场景数、未通过场景的问题清单、整章字数与目标偏差、本次登记的提示问题，以及不影响写作的附注（例如问题登记失败）。

### 改写工作流

- 发起参数：章节、目标、主创整理的修改要求。目标二选一：
  - 段号 `{paragraphs: {from, to?}}`，从 1 开始，含两端；
  - 原话 `{quote}`：编辑器选区是渲染后的文字，比较时两边都去掉空白和 `*`、`_`、`` ` ``、`~`、`#`、`>`，必须恰好出现一次；跨段选区扩展到涉及的全部段落。
- 段落与场景切分同一口径（以空行分隔的块，代码块内的空行不分段）。
- 需要文风文件和非空正文，否则停止（`style`、`no-prose`）；目标越界、找不到或出现多次时停止（`target`），都不调用模型。
- 助手：
  - 规划输入含修改要求、上下文窗口、本章写作指导、本章参考文件路径；提交 `{rewrite, issues?}`，校验与退回规则同场景规划，摘录合计不超过 3000 字；
  - 审阅提交 `{rewriteReview: {passed, problems}, issues?}`，不通过时问题清单必填；
  - 一次运行的规划与审阅共用一个临时会话。
- 写手每次都是新的临时会话；审阅不通过时附问题清单重写，首写之外最多重写 2 次，仍不通过即停止（`rewrite-failed`）。
- 确认：待应答项 `approve`，标题“确认替换改写段落”，说明是新旧对照；应答为布尔值或 `{approved}`，放弃时结果为 `discarded`，正文不变。
- 替换：
  - 按目标原文在当前正文中重新查找：原位置仍匹配时替换原位置；否则原文恰好出现一次时替换那一处，目标之外的改动不阻止替换；
  - 找不到或在别处出现多次时不替换，停止（`target-changed`）；
  - 只替换目标段落，文件头（含 `source`）原样保留：依据记录的是整章写作时的规划版本，局部改写不改变它；
  - 重放时目标已被替换为改写结果的，按已替换处理，不重复写入。
- 改写与整章写作共用每章一次运行的限制；`continue_writing` 对中断或意外失败的改写同样按记录重放，其余情况只续写整章写作。
- 运行结果记录结束方式与原因、目标段号范围、原文与改写结果、重写用尽时的问题清单和附注。

### 运行、停止与续写

- 同一章同时只能有一次运行：本进程正在执行、等待核对、或运行记录显示中断（进程退出时仍在运行）时，发起被拒绝（`RUN_ACTIVE`，HTTP 409）。
- 续写取本章最近一次运行：
  - 中断或意外失败：按运行记录重放，已完成的步骤（含模型调用）不重复执行；
  - 已停止或已完成：新开一次运行，带上检查点。依据及资料来源未变时沿用已确认规划；若规划未完成，先从第一个未确认场景继续规划，全部确认后从第一个未通过正文审阅的场景写作；
  - 依据或资料来源已变：保留已写前缀，重新规划并审核未写场景；已写场景须与当前切分的同序场景在细纲、标题、原文上一致，否则停止（`resume-mismatch`），由用户改为整章重写；
  - 旧版本运行记录保留；不能按新版步骤直接重放，续写先关闭旧运行，再由新版本流程恢复可用检查点。
- 停止：取消正在进行的调用。中断的运行不在本进程执行，按记录重放到下一步即转为已取消，不产生新的模型调用。已停止的运行对外 `error` 为空，Kernel 的取消文本不交给用户和主创。
- 写入正文失败：本场景不算通过，续写时重做本场景。
- 其他错误码：
  - `RUN_NOT_FOUND`（404）：续写时本章没有运行，或运行 id 不存在；
  - `RUN_ANSWER_INVALID`（400）：应答时运行不在等待，或没有答全待应答项。

### HTTP 运行接口

接口在 `/api/projects/writing/<route>`，只接受已打开的 Project，错误码映射同上。发起写作和改写不开放 HTTP，只经主创。

| 路由 | 参数 | 返回 |
|---|---|---|
| `GET runs` | `chapterEntryId` | 本章运行摘要，按发起先后；含已开始、尚未落盘的运行 |
| `GET active-runs` | 无 | 本项目进行中、等待确认或中断的运行摘要，界面据此标记“写作中”并锁定正文，中断的运行不锁定 |
| `GET run` | `runId` | 进度（`WritingRunProgressDto`） |
| `POST stop` | `{runId}` | 停止后的进度 |
| `POST continue` | `{chapterEntryId, mode?}` | 续写开始时的进度 |
| `POST answer` | `{runId, key, decision}` | 应答后的进度 |
| `GET chapter-session` | `chapterEntryId` | `{chapterEntryId, sessionId}`，尚无会话时 `sessionId` 为 null |
| `POST chapter-session` | `{chapterEntryId, fresh?}` | 本章当前会话，没有时创建；`fresh: true` 时总是新建 |
| `GET chapter-sessions` | `chapterEntryId` | 本章会话列表 `{sessionId, title, updatedAt, preview?}[]`，按更新时间倒序 |
| `POST delete-chapter-session` | `{chapterEntryId, sessionId}` | 归档该会话，返回剩余列表；本章有运行、主创回复中或等待回答时拒绝（`RUN_ACTIVE`） |
| `GET role-models` | 无 | 主创、助手、写手三个角色的模型设置（本作品设置与实际生效值）和启用模型列表 |
| `POST role-model` | `{role, settings}` | 保存一个角色的 `modelKey`、`reasoningEffort`、`temperature`，为空表示沿用全局；未启用的模型拒绝（`MODEL_INVALID`） |

- 进度：
  - 每次从运行记录投影，不另存，刷新页面或进程重启后显示一致；
  - 准备完成就显示整章场景列表，状态为待规划、规划中、待写、写作中、审阅中、重写第 N 次、已通过、未通过。当前规划或资料审核的场景标为规划中，已确认规划但还没有正文的场景标为待写；
  - 停止或中断在规划阶段时，未确认场景显示待规划，续写保留已确认规划；停止在正文场景中途时，该场景显示待写，续写会重写它；
  - 每次尝试带渲染后的写手提示、写手产出和程序判定；改写另带目标段号、原文和最近一次通过审阅的新段落；
  - 投影按两个工作流的调用顺序解读记录，工作流步骤变化（manifestHash 升级）时须同步修改。
- 应答：
  - `decision` 为 `{approved, comments?}`（讨论模式的用户确认，退回时意见必填）或 `{replace}`（改写确认），须与 `key` 对应的待应答项一致；
  - 主创核对只由主创应答，界面应答被拒绝（`RUN_ANSWER_INVALID`）。
- 报告：续写与应答后，停下时的报告交回本章写作会话；本章没有会话（被归档）时照常推进，不发报告。停止不另发报告，跟踪这次运行的后台任务会以“已停止”结束。
- 章节会话：
  - 一章可以有多个主创会话，标签 `writing-chapter:<chapterEntryId>`，按本项目的主创会话查找，已归档的不算；
  - 最近更新的会话是这一章的当前会话：界面默认打开它，续写与应答后的报告也交回它；
  - 创建时初始值 `{chapterEntryId}`，标题“写作 <章节标题>”；同一章的并发“没有才创建”只建一个会话；
  - 删除即归档，会话文件保留。
- 角色模型设置：
  - 存在本作品的 Project Config，`agent.profiles.<writing.lead|writing.assistant|writing.writer>.model`，只改这三个字段，其他 Profile 与字段原样保留；
  - `reasoningEffort: "off"` 即关闭思考；`temperature` 取 0 到 2，按 Profile 配置作为 Provider 请求参数，低于单次调用的显式覆盖；
  - 助手与写手每次调用都新建会话，新设置从下一次调用生效；主创会话创建时绑定模型，保存主创设置后界面让当前会话清掉单独的模型与思考选择，下一轮按新设置解析。

### 场景与素材

- Markdown 结构按行扫描：
  - 代码块内的 `#` 不算标题，空行也不分段；
  - 标题只认 ATX 形式（`#` 开头）；
  - 段落是以空行分隔的块。
- 细纲按模板解析：HTML 注释不计入内容；字段行写作“- 字段名：值”，不是字段行的文字续接到上一个字段；具体情节的缩进子项并入上一条。
- 细纲结构检查由大纲模块的 `analyzeDetailStructure`（`shared/outline-detail-structure.ts`）完成，细纲分析、正式采用、编辑界面与写作共用；写作时细纲有阻断项或本章有多份细纲，整章都不切分，返回阻断问题 `MISSING_SCENE_STRUCTURE`，说明列出各项原因。
- 场景一览：每项是场景编号、名称（没有名称时写“场景 N”）、字数和结尾落点，当前场景标“当前”；场景 1 没有上一场景，最后一个场景没有下一场景，对应行写“（无）”。下一场景只给名称和场景简述，标明只用于结尾铺垫。
- 必须写到的要素：
  - 具体情节逐条原文在前；
  - 伏笔渲染为“伏笔（<动作>）：<标记原文>；效果：<效果>”，效果为空时省略；
  - 场景认领的伏笔标记在章节大纲中找不到或状态不一致时整章阻断（细纲结构检查已拦截）；章节大纲中没有分给任何场景的伏笔标记登记提示问题 `UNASSIGNED_FORESHADOW`；场景认领的标记属于尚未确认的伏笔时，交接不带它，写作不执行，同样登记 `UNASSIGNED_FORESHADOW` 并定位到场景。
- 各场景字数要求之和与细纲总览目标字数相差超过 50% 时，登记提示问题 `WORD_TARGET_MISMATCH`。
- 交接的待补参考资料警告转为提示问题 `PENDING_REFERENCE`；场景参考资料中有链接但不可读的路径在场景规划校验时同样提示。
- 本章写作指导只取章节大纲的 `writingGuidance`；场景的写作指导在本场景部分渲染。
- 本章伏笔：只取交接给出的标记原文和动作，伏笔标题等定义字段不进入素材。

### 其他程序字段

- 字数口径：
  - 统计非空白字符。
  - 不计入的内容：
    - HTML 注释；
    - 代码块围栏行；
    - 分隔线；
    - 行首的标题、引用、列表标记；
    - 成对的强调与删除线符号；
    - 反引号；
    - 链接与图片的地址，只保留文字。
  - 单个 `~` 和 `_` 按普通字符计。
  - 写作容差与规划一致性检查都是目标的上下 50%，含边界。
- 文风文件：
  - 先去掉文件头，再按二级标题取小节；三级及以下标题属于所在小节的正文。
  - 同名小节重复时报错。
- 上一章：
  - 在概览的章节序列中往前找，取最近一个恰有一份非空正文的章节；
  - 归属冲突的章节跳过；
  - 找不到时返回空，由写作工作流登记 `MISSING_PREVIOUS_CHAPTER`。
- 上一章结尾：
  - 从末尾按完整段落累计，不超过 1500 字；
  - 最后一段单独就超限时，从句末处截断；
  - 没有句末时，按字数硬截。
- 摘录：
  - 位置是 `{path, heading}` 或 `{path, paragraphs: {from, to?}}`。
  - 标题必须全文恰好出现一次，小节到下一个同级或更高级标题为止。
  - 段落从 1 开始计数，包含两端。
  - 摘录文件由调用方按助手的可读范围预先读入；未读入的路径一律视为不可读。

### 结构校验与渲染

- 所有提交都严格校验，多余字段拒绝。
  - 结构 A 不接受问题字段，问题通过问题登记单独提交。
  - 校验失败时返回全部原因，供退回助手。
- 结构 A：
  - 场景须与切分结果按编号和一级标题文本逐一对应；
  - 效果、人称、锁定要素等程序字段不接受助手提交；
  - 写作手法补充、背景知识与追加要素可以为空；
  - supplements 为按需资料数组，每项包含 kind、subject、points 与至少一项 excerpts 来源定位；每个参与角色恰好对应一项 character，明确角色引用须实际使用。不接受新增或重复角色，来源和摘录限制与手法/背景共用。
  - 程序保存资料来源内容摘要，审核后及正文写入前复核；来源变更停止写作，续写重新整理与审核。
  - 章节依据由程序从交接结果写入。
- 结构 B：
  - 系统部分：固定的写手职责，以及文风的三个小节，各为独立条目；
  - 用户部分：各小节各为独立条目，按本规范的顺序排列，内容为空时写“（无）”；
  - 「上一章结尾」与「上次的问题清单」始终作为条目出现，不适用时内容写占位说明，不整段省略；
  - 伏笔动作渲染为埋设、强化、回收。
- 结构 C：
  - `elements` 必须与必须写到的要素逐项同序对应，`forbidden` 必须与本章禁止事项逐项同序对应；
  - 不通过时，问题清单必填；
  - `judgeScene` 在以下情况判为不通过，并汇总原因：
    - 写手输出为空；
    - 助手判定不通过；
    - 有要素未写到；
    - 有禁止事项出现；
    - 字数超出容差。
- 结构 D：
  - 修改要求和人称必填，摘录限制与结构 A 相同；
  - 可提交同样的 supplements，独立审核原始修改要求、目标上下文与补充稿后才调用写手；确认替换前再核对来源。
  - 章首或章末没有上下文时，对应小节给出说明文字；
  - 改写审阅不通过时，问题清单必填。

### 写手提示词的默认条目

- 内置默认由 `shared/prompt-management/writing-templates.ts` 的三份小节数组声明，是唯一真相源：提示词管理的内置默认条目、以及没有绑定会话时的兜底渲染都消费同一份数组，保证两条路径逐字一致。
- 两个用途共用 `WRITER_SYSTEM_SECTIONS`（写手职责、文风要求、禁用写法、样文），再分别接 `SCENE_WRITER_SECTIONS`、`REWRITE_WRITER_SECTIONS`。
- `writing-catalog.ts` 用 `promptVariableNames` 收集变量，除 `forbidden`、`sample` 外都是必需变量；`validatePromptEntries` 在保存与即时开关时据此拒绝缺失。
- `structures.ts` 的 `renderScenePrompt`/`renderRewritePrompt` 不再自行拼接整块模板，而是把变量交给 `renderManagedPrompt` 渲染内置小节，取回 `{system, user}`；没有绑定会话时也走这条路径。
