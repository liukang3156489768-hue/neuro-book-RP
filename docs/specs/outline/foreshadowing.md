# 伏笔库与标记派生

## 目标与非目标

本能力保存伏笔设计并从正式章节大纲中的结构化标记派生埋设、强化和回收情况。本能力不使用正文作为状态来源，不把 Agent 一次推断直接视为正式标记，也不增加超出四种用户可见状态的生命周期状态。

## 术语与参与者

伏笔条目包含稳定 ID、设计内容和来源记录。设计内容包括名称；分开保存的表面呈现线索与背后关联；埋设建议（出现情境、呈现方式、暗示程度）；回收建议（揭示条件、前后呼应方式、预期效果）。埋设标记表示在章节大纲中引入或强化伏笔，回收标记表示在章节大纲中完成回收。用户可创建和确认标记；模块 Agent 可提出标记建议；解析器只处理正式有效的大纲标记。

## 输入与前置条件

伏笔可手动创建或由用户灵感生成，初始为草稿。伏笔定义保存于 `outline/foreshadowing/<slug>--<stable-id>.md`；正式章节大纲正文使用以下 Markdown 注释包围可见文本的结构化标记：

```markdown
<!-- nb:foreshadow marker="fm-01" foreshadow="fo-001" action="plant" -->银纹<!-- /nb:foreshadow marker="fm-01" -->
```

`action` 只能是 `plant`、`reinforce` 或 `recover`；`marker` 在文档内唯一，开始和结束注释必须成对。UI 将有效标记表现为类似文档注释的下划线和悬浮信息。一个章节可多次埋设或强化同一伏笔；回收必须在同一方案线路图的格号上晚于有效埋设（同一节点内按标记位置先后；不同节点同格不算“之后”），否则只产生异常，不得成为有效回收。先后按格号跨线路判定，埋设与回收可以位于同方案的不同固定线路。

## 输出与可观察行为

伏笔库只展示四种状态：草稿、待使用、已埋设、已回收。状态规则为：没有有效埋设则待使用；有埋设而无有效回收则已埋设；存在有效回收则已回收。界面可追溯全部埋设/回收章节、标记原文和关联大纲。删除或修改标记后自动重算。

已过章节数是派生指标，不是状态：

- 按方案计算，单位是线路图格数：已回收时为回收格号减埋设格号；未回收时为该方案所有有效固定章节节点中最大格号减埋设格号；
- 起点为该方案首个有效埋设所在格；
- 不以正文完成情况计数；移动节点、插入列或线路变更后重新计算；
- 同一伏笔出现在多个方案时，分方案显示。

## 状态与转换

| 事件 | 状态/结果 | 备注 |
|---|---|---|
| 创建未确认设计 | 草稿 | 不参与正式状态派生 |
| 用户确认设计 | 待使用 | 尚无有效埋设 |
| 正式大纲新增埋设 | 已埋设 | 可重复埋设/强化 |
| 正式大纲新增有效回收 | 已回收 | 记录回收位置 |
| 删除或失效标记 | 按剩余有效标记重算 | 不直接手填状态 |
| 回收早于埋设或标记损坏 | 保持四状态规则并产生异常 | 不新增状态 |

Agent 建议标记在讨论模式下必须逐项确认；自动模式可依持续授权执行，但删除仍需审核。任何参与者都只能通过增删改正式标记改变状态，不存在直接写状态或派生字段的操作。

## 副作用与数据

伏笔定义、正式标记、解析结果、来源章节、异常报告、建议审批和历史记录按项目持久化。结构化项目文件是规范来源，SQLite 只保存可重建索引和解析摘要。状态是由正式大纲标记计算的派生值，并按同方案线路图的格号校验先埋设后回收，可在文件重建后重新计算。只有当前分析报告有效且节点仍有效的固定线路可贡献正式来源；已失效节点不授予资格。多条固定线路共享的节点按节点去重，只计一次。同线路其他有效章节的标记仍逐章保留，不因局部失效而清空。正文内容、聊天上下文和草稿标记不得成为状态来源。

## 失败与恢复

标记语法损坏、引用不存在或版本过期时，解析器保留原文、报告异常并拒绝把不确定标记用于正式状态；允许 Agent 提出修复草案，用户确认后再写入。部分解析失败不得清空既有解析结果；恢复时重新扫描规范来源。

## 边界与兼容

本能力拥有伏笔生命周期派生和标记语义，不拥有章节顺序或正文写入权限。跨方案中的同一伏笔按稳定 ID 汇总，无需区分由哪一条方案回收。

## 验收与 Smoke

- Given 已确认但无埋设的伏笔，Then 状态为待使用；加入正式埋设后为已埋设；再加入有效回收后为已回收。
- Given 同章两次埋设和一次回收，Then 全部来源可追溯，状态为已回收。
- Given 删除唯一埋设标记，Then 状态自动回到待使用；正文变化不影响状态。
- Given 损坏标记或先回收后埋设，Then 保留原文并提示异常，不静默生成错误正式结果。

## 实现合同

伏笔 schema 为 `nbook.outline-foreshadowing/v2`，在 `title`、`body` 之外有可选分项 `surface`、`connection`、`plant: {situation, presentation, subtlety}`、`recover: {condition, echo, effect}`；创建时可写入，编辑时缺省沿用、显式 null 清除。已过章节数由 `deriveForeshadowingElapsed` 按方案从已固定线路节点的格号派生，经伏笔状态接口和规划 Agent 的伏笔上下文返回，工作台卡片只读显示；工作台伏笔库已提供定义与分项的直接编辑（自动保存，已确认的伏笔修改前需确认回到草稿）和确认界面，章节大纲正文可在富文本编辑器中选中文字从浮动菜单插入、切换和移除标记；状态、来源和已过章节数仍只展示服务端派生结果。已有规范文件草稿／确认、标记解析器及版次、固定线路四状态派生、来源和先回收异常的服务端实现。正式读取及写入对损坏、未知伏笔 ID、未知动作或未成对标记 fail-closed；伏笔只读视图在 manifest/hash/front matter 有效时逐章节隔离标记异常，显示诊断并保留其他章节的正式来源，原文件不被覆盖。规划 Agent 的标记建议工具按动作区分 plant（新增埋设，章节没有任何标记时也用它）、strengthen（新增强化）、resolve（新增回收）与 repair，候选正文必须含对应动作的标记；规划 Agent 已能读取局部损坏诊断并生成带 proposalId 的待审批建议；损坏章节另有专用 repair 预览／提交事务，候选仍须严格解析，章节修改后回到 draft。TipTap 标记编辑器和工作台异常展示已有组件合同。完整 Nuxt／浏览器验收、默认全包和真实模型仍未完成，故本 Spec 维持 planned。
