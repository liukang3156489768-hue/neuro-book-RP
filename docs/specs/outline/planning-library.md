# 大纲库与细纲

## 目标与非目标

本能力为作品提供可复用的灵感与方案库，管理总纲、卷纲、章节大纲及其细纲。正文写作以大纲库的层级为准：写作方案中的卷纲、章节大纲顺序就是正文的章节顺序（见 [outline.writer-handoff](writer-handoff.md)）。本能力不生成正文，不把草稿交给写作模块，也不替用户决定唯一方案。

## 术语与参与者

- 总纲：一个方案的纲领，每个方案恰好有一个。
- 方案链：同一作品的一个完整展开方案，可存在多条；每个方案各有一个总纲，并各自组织卷纲、章节大纲。方案之间默认各用各的总纲，互不影响；只有用户或模块 Agent 手动建立关联后，才共用同一个总纲条目。
- 提取方案：由作品提取流水线（见 [inspiration.outline-extraction](../inspiration/outline-extraction.md)）创建的方案，其结构与内容与普通方案一致，可被编辑、被写作模块选用。
- 来源提取细纲：由提取流水线写入、以原作文引用为采用依据的正式细纲，见“细纲的采用依据”。
- 章节大纲：可被线路节点引用的剧情规划单元，与正文一对一。
- 细纲：依托章节大纲的场景细化，可有一个或多个连贯片段。
- 用户：可编辑、确认、删除和处理冲突的人类操作者。
- 模块 Agent：可按授权生成建议和执行规划操作，但不写正文或 `lorebook/`。

## 规范文件与领域边界

结构化项目文件是本能力的规范来源，SQLite 只保存可重建索引、查询加速数据和解析摘要。大纲、卷纲、章节大纲和细纲保存于 `outline/entries/<slug>--<stable-id>.md`，使用 YAML front matter 保存结构化字段、Markdown 正文保存叙述内容；模块版本和顶层索引保存于 `outline/manifest.yaml`。稳定 ID 不因移动、重排、改名或关系变化而改变。

对象删除与关系删除分开：对象删除是删除规范文件，关系删除只移除父子、引用、节点关联或线路成员关系。被其它方案挂载或被线路节点关联不阻止对象删除：容器条目级联删除全部子孙条目，所有方案中指向被删条目的挂载关系一并清理，关联的线路节点保留并标记失效，由用户后续修复。删除前必须预览并展示外部引用、受影响线路节点和级联条目数，经用户确认并记录历史后提交。

本能力拥有大纲库和细纲规划语义，不拥有正文、`lorebook/` 或线路最终顺序；与现有 Plot 互补，不替换或复制 Plot 的 Story、Thread、Scene、Promise、Decision、World Engine 关联和 Writer Brief。

## 输入与前置条件

用户可手动新建条目，或提供简单方向请求生成草案。创建和编辑必须带项目身份、稳定 ID、父级关系和当前版本。跨方案复用通过引用同一条目实现。修改共享条目前必须提示影响范围并由用户确认写时分叉；分叉产生新文件、新稳定 ID 和不同名称，不覆盖源文件且不重新合并。目标方案的线路若仍引用源条目，须先处理线路节点；分叉不得留下悬空引用，也不得默默将固定线路改绑到新草稿。

细纲正式保存前必须完成 AI 偏差/冲突分析并允许用户选择保存为草稿或正式文本。章节大纲可没有细纲，但细纲不得脱离章节大纲正式存在。

细纲分析与审阅只以上游链为依据：总纲、所属卷纲（如有）、所属章节大纲，以及细纲在方案中的挂载位置。上游链中任一条目内容变化、细纲改挂到别的章节，或细纲被挂入另一方案时，已采用细纲在同一次提交中回到草稿并清除分析报告，需要重新审阅。同章其他细纲、其他章节或卷纲、方案标题以及条目排序的变化不影响已审阅细纲，因此同一章的多份细纲、同一方案的多个章节可以同时保持已审阅。

## 内容要素

- 卷纲与章节大纲写明起点、主要发展、关键事件、转折和阶段落点。
- 细纲正文覆盖：本章承接的局面、主要内容和结束位置；场景顺序、人物行动、事件发展和场景衔接；必须呈现的细节、对白意图、信息披露和已有伏笔安排。细纲完成必要的剧情决定，但不逐句指定正文措辞。以上作为生成草案和偏差分析的检查清单，不强制拆成结构化字段。
- 写作指导可以整条设置，也可以锚定到细纲中的某一段原文，推荐说明展开或略写、手法和重点。
- 参考文件标注写明资料、所用部分和用途，可以整条设置，也可以锚定到某一段原文；没有实际可查阅来源时标记为“待补”，不得编造路径或内容。“待补”不阻止正式采用，但要在偏差分析结果和正文交接中作为告警出现。
- 篇幅支持章节总目标字数，必要时按场景分配大致字数。

## 输出与可观察行为

界面以阶梯式层级显示多条方案链，每条方案链以自己的总纲为根；多个方案关联同一总纲时，该总纲在各方案下均显示并标出“被多个方案共用”。支持新增、删除、移动、重排和展开条目。章节大纲显示正文、伏笔使用/回收标记和素材索引，并可在同一详情中查看其细纲及标注；细纲显示素材索引、写作指导、参考文件和篇幅要求。草稿、正式采用、埋设伏笔、回收伏笔作为条目标记展示；正式采用、且细纲已审阅的章节大纲进入正文写作上下文，不要求在线路中固定。

生成结果先显示为可审阅草案。正式保存时显示分析结果、偏差和冲突；失败时保留草稿并阻止正式采用。

## 状态与转换

| 事件 | 结果 | 拒绝条件 |
|---|---|---|
| 新建/生成 | 草稿条目 | 项目身份或父级无效 |
| 用户确认正式采用 | 正式条目 | 必需分析失败或存在未处理冲突 |
| 共享引用位置修改并确认 | 新分叉条目 | 用户取消则原引用不变 |
| 新建方案 | 方案带一个新建的空总纲 | 项目身份无效 |
| 手动关联总纲 | 方案改为引用另一方案的总纲；原总纲条目不被自动删除，仍可在条目库中找到并由用户删除 | 方案当前总纲有正文且用户未确认改用目标总纲；目标总纲不存在 |
| 解除总纲共用 | 被共用的总纲写时分叉出当前方案专属总纲 | 用户取消则保持共用 |
| 删除条目 | 删除关系或对象，分别处理；对象删除级联子孙并清理全部挂载 | 预览未确认；孤立总纲未二次确认；总纲仍被方案使用 |
| 细纲保存 | 草稿或正式 | 正式保存未完成分析 |
| 提取流水线写入细纲 | 采用依据为“来源提取”的正式细纲 | 缺少原文引用 |
| 用户编辑来源提取细纲正文 | 转为普通细纲，适用常规分析与审阅规则 | 无 |

移动和重排不改变稳定 ID。一个方案不能拥有第二个总纲对象，也不能没有总纲，因此仍被任一方案使用的总纲不能删除，预览须列出使用它的方案，并提示先让这些方案改用其他总纲或删除这些方案；未被任何方案使用的孤立总纲才可删除，且需要二级确认。删除按条目规范父级级联，预览须列出被级联波及的方案。删除级联影响必须先展示预览。

### 细纲的采用依据

细纲的正式状态带“采用依据”，分两种：

- **分析审阅**（普通细纲）：正式采用前须完成偏差与冲突分析；上游链变化时回到草稿，规则见“输入与前置条件”。
- **来源提取**：由提取流水线写入，依据是原作文引用（条目 frontmatter `basis.sources` 中的来源文件与段落范围），不做偏差分析，视为已审阅，可被正文写作模块读取。这类细纲不适用“上游链变化即回到草稿”，因为其依据是原文而非上游规划。

用户修改来源提取细纲的正文后，该细纲转为分析审阅依据：回到草稿，之后适用常规规则。仅移动、重排或改变所属方案不改变其依据。

## 副作用与数据

条目、引用、版本、草稿/正式状态、素材索引、细纲和分析结果必须按项目持久化并进入可追溯历史。结构化项目文件是唯一规范来源，SQLite 只作为可重建索引、查询加速数据和解析摘要；不得双写为两个独立真相源。每次正式变更应能够从文件重建层级和引用关系，索引损坏不得反向覆盖规范文件。

## 失败与恢复

父级不存在、引用失效、版本冲突、分析超时或文件损坏时拒绝正式提交，保留用户原文和草稿。用户取消分叉、删除或级联操作时不改变源条目。重开项目后从规范来源恢复；索引损坏时可重建，不以空索引覆盖文件。

## 边界与兼容

本能力拥有大纲库和细纲的规划语义，不拥有正文或 `lorebook/`。本能力不提供从旧笔记或设计文档导入规划的通用导入；来自作品的大纲只能通过 [inspiration.outline-extraction](../inspiration/outline-extraction.md) 以提取方案形式写入，写入必须经本能力的领域操作与历史。

总纲从“全局唯一”改为“每方案一个”是对既有数据格式的变更：manifest 须使用新的 schema 版本表示方案与总纲的对应关系；读取旧版 manifest 时，按“所有方案共用原全局总纲”解释，保持已有共用关系，不改写用户文件，也不要求迁移数据；新版文件在旧版本中必须被明确拒绝而不是被误读。

正文写作模块只通过 [outline.writer-handoff](writer-handoff.md) 只读读取。

## 验收与 Smoke

- Given 新项目，When 创建两个方案并共享一个条目，Then 两个方案各有一个互相独立的总纲，两个位置引用同一条目稳定 ID，且共享条目修改确认后只在当前位置产生新 ID。
- Given 两个方案各有总纲，When 手动把方案 B 关联到方案 A 的总纲，Then 两个方案引用同一总纲条目；When 在方案 B 修改该总纲并确认，Then 产生方案 B 专属的新总纲，方案 A 不变。
- Given 旧版 manifest（单个全局总纲、多个方案），When 打开项目，Then 各方案仍共用该总纲，用户文件不被改写；旧版本读取新版 manifest 时明确拒绝。
- Given 提取流水线向方案写入细纲，Then 该细纲为带原文引用的正式细纲，无需偏差分析即可被写作模块读取；When 修改其所属章节大纲，Then 它保持正式；When 用户编辑其正文，Then 它回到草稿并适用常规审阅。
- Given 章节大纲保存细纲，When 选择草稿，Then 不触发正式使用；When 选择正式，Then 必须展示分析结果并在冲突未处理时拒绝。
- Given 同一章有两份细纲，When 依次审阅并正式采用，Then 两份都保持已采用；When 改写该章节大纲，Then 两份都回到草稿。
- Given 被其它方案挂载或被线路节点关联的条目，When 请求删除，Then 先显示引用、受影响节点和级联预览；确认后删除条目及其子孙，清理所有方案中的挂载，关联节点标红待修复。
- Given 关闭并重开项目，Then 层级、引用、版本和草稿/正式状态可恢复。

## 实现合同

条目 schema 为 `nbook.outline-entry/v2`，v1 文件仍可读取并在解析时归一为 v2。参考文件为 `references: {path?, locator?, purpose?, pending?}[]`：非待补项必须有 `path`，待补项可无路径但必须用 `locator` 说明所需资料，旧 `referenceFiles` 路径数组读取时转换，二者同时出现即拒绝。细纲的写作信息全部写在正文模板里（见 [outline-entry-templates.md](./outline-entry-templates.md) 的“细纲”），frontmatter 不读取也不保存 `writingGuidance`、`references`、`targetWords`；旧的段落标注与 `guides`、`scenes`、`perspective` 已移除，解析旧文件时忽略。进入正式分析的细纲必须是当前规范序列化，否则提示先保存一次，避免采用后正文交接因来源 hash 不一致而失效。工作台大纲库已提供方案链、条目、共享条目写时分叉、上述字段以及细纲分析与正式采用的编辑界面；各级条目选中即直接编辑（富文本正文、自动保存，总纲、已采用条目和共享条目的修改须先确认或另存），行为见 [workbench-ui.md](./workbench-ui.md)，写入全部经领域操作，删除先预览影响；浏览器验收未执行。其余进度见 [t04](../../../.agents/works/w00018-outline-planning-module/tasks/t04-outline-library-and-detailed-outline/README.md)。实现不得将 Plot 实体复制为第二套 Scene 真相源。

manifest schema 为 `nbook.outline/v3`：无顶层 `totalId`，每个 `plans[]` 条目带 `totalId`，校验要求其指向一个总纲条目且在该方案中恰好有一个 `parentId` 为空的挂载；允许存在未被任何方案使用的总纲条目。读取 v1／v2 时把原全局 `totalId` 注入每个方案，磁盘文件不改写；v3 在旧读取路径以 `UNSUPPORTED_SCHEMA` 拒绝。领域动作 `create-plan` 同时创建空总纲并返回其 ID，`associate-total` 与 `unshare-total` 是改变方案总纲的唯一入口，通用发布路径不能改动任一方案的 `totalId`；`create-total` 与 `edit-entry.confirmGlobal` 已移除。被两个以上方案共用的总纲不能原地编辑，须经写时分叉。`attach-entry` 对规范父级是总纲的条目，允许以目标方案自己的总纲作为 `parentId`。删除预览的 `usedByPlanIds` 为使用该总纲的方案，`affectedPlanIds` 为被级联波及的方案。已知限制：孤立总纲的级联按条目规范 `parentId` 进行，若仍有方案挂载以它为规范父级的条目，这些条目随之被删除，其所在方案由 `affectedPlanIds` 在预览中提示。

细纲的采用依据存于可选的 frontmatter 字段 `basis: {kind: "source-extraction", sources: [{path, locator}]}`；缺省即分析审阅，旧文件读取与序列化不变。格式层只接受 `status: adopted`、无 `analysis`、`sources` 非空且每项 `path` 与 `locator` 非空的细纲带 `basis`。写入入口是 `library.ts` 的 `prepareSourceExtractionDetail`（挂在方案内的章节大纲下，章节大纲可仍是草稿），它不是 `LibraryAction`，HTTP 与 Agent 动作 schema 到不了；原始发布本就拒绝改写条目文件，因此用户与普通 Agent 无法设置 `basis`。`assertDetailReviewed` 对带 `basis` 的细纲直接视为已审阅；`invalidateDependentDetails` 跳过它们（`detailReviewScope` 只服务分析审阅，无需改动）。`edit-entry` 与写时分叉清除 `basis` 并回到草稿；`move-entry` 保留 `basis` 与正式状态。引用是否落在本章范围内由提取流水线在调用前校验，格式层只保证引用存在。
