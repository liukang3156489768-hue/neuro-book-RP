| 2.3 Detailed outline（细纲 Agent） | 作为模块主 Agent 的子 Agent | 内容要素见 S1–S5 |
| 2.5 foreshadowing（伏笔设计 Agent） | 作为模块主 Agent 的子 Agent | 设计产物见 S7 |
| 3.1 大纲库、3.2 故事线可视化、3.3 伏笔模块 | 由新模块替换 | 分别对应大纲库、线路规划和伏笔库 |
| 4 伏笔状态与程序维护 | 由新模块替换 | 三状态改为四状态；章节计数见 S8 |
| 5 规划 Agent 权限 | 由新模块替换 | 改为讨论／自动模式；任务范围授权见 S11 |
| 6.1 前四行产物归属 | 由新模块替换 | 规划产物归模块所有 |
| **2.1 writer.pro** | **保留，按原始设计开发** | 新建 Agent，不改造现有 `writer` |

| **1.3 链路后半段** | **保留** | 细化成果 + 既定人称与文风 → writer.pro → 正文；上游改为读取新模块的固定线路 |
| **6.1 正文行、6.2 文件与界面一致性** | **保留** | 正文由 writer.pro 产出并写入正文文件 |
| **8 中 01–04 及 05 的 writer 部分** | **保留** | writer.pro 输入、细纲表达边界、文风与文献、篇幅与交付仍待细化 |

writer.pro 与新模块的接口：原始设计中 writer.pro 的“细纲、写作指导、参考文献、字数要求”由 Detailed outline 提供，现在改为读取新模块线路规划中已固定的正式章节大纲和正式细纲；“主要视角”和“文风参考”仍承接用户或作品既有选择。

## 2. 可补充进新设计的内容

下表只列原始设计中新设计没有、或只写得很笼统的内容。“现状”一栏按当前 Proposal 和 `packages/neuro-book/server/outline/format.ts` 的 schema 判断。

### 大纲库与细纲

**S1 细纲正文的内容要素**（原 2.3）
- 原始：本章承接的局面、主要内容和结束位置；场景顺序、人物行动、事件发展和场景衔接；必须呈现的细节、对白意图、信息披露和已有伏笔安排。
- 现状：Proposal 1.3 只列出四类标注（素材索引、写作指导、参考文件、篇幅），没有定义细纲正文应覆盖什么；schema 中细纲只有自由文本 `body`。
- 建议：作为细纲正文的内容清单，供 Agent 生成细纲草案，以及正式保存前的 AI 偏差与冲突分析检查“是否缺承接、缺结束位置”等。先作为清单，是否拆成结构化字段另议。

**S2 细纲的详细程度**（原 2.3）
- 原始：细纲需完成必要的剧情决定，同时保留语言表达空间，不要求逐句指定正文措辞。
- 现状：新设计没有写细纲的详细程度。
- 建议：写入细纲设计，作为 Agent 生成细纲和 writer.pro 表达边界的共同依据。

**S3 参考文件的定位、用途与“待补”**（原 2.3、3.1）
- 原始：参考文献要写明哪份资料、哪一部分、使用目的；必须有实际可查阅来源，未取得的资料标记“待补”，不编造引用。
- 现状：Proposal 只写“需要先阅读哪些资料”；schema `referenceFiles` 只是路径数组，没有片段定位、用途和待补状态。
- 建议：参考文件标注增加片段定位、用途说明和“待补”标记；Agent 不得为缺失资料虚构路径或内容。“待补”的参考文件是否阻止细纲正式采用，需要确认。

**S4 写作指导的维度与对应位置**（原 2.3、3.1）
- 原始：指导要说明哪些内容展开、哪些略写，采用什么手法，重点表现什么；指导和文献标注需对应具体场景或内容。
- 现状：Proposal 用注释形式承载指导，方向一致；schema `writingGuidance` 是整篇一个字符串，无法对应到场景。
- 建议：明确写作指导按场景或片段锚定，并把“展开／略写、手法、重点”作为指导的推荐维度。

**S5 按场景分配篇幅**（原 2.3）
- 原始：确定本章篇幅，必要时分配各场景的大致字数。
- 现状：Proposal 的“补充建议”提到片段字数分配但未确认；schema `targetWords` 是单个数字。
- 建议：与 S4 一起确认篇幅的表达形式（总字数、区间、按场景分配）。

**S6 卷纲与章节大纲的骨架要素**（原 2.2）
- 原始：把想法整理为故事骨架，明确起点、主要发展、关键事件、转折和阶段落点。
- 现状：新设计对总纲、卷纲的内容描述较宽泛，缺少“起点”“阶段落点”。
- 建议：作为方向生成时 Agent 输出卷纲和章节大纲的要素清单。

### 伏笔库

**S7 伏笔设计的结构化内容**（原 2.5）
- 原始：名称及编号；伏笔内容，分“表面呈现的线索”和“背后的关联”；埋设建议，含出现情境、呈现方式、暗示程度；回收建议，含揭示条件、前后呼应方式、预期效果。
- 现状：Proposal 2 列出意图、预期效果、回收条件等，但没有“表面线索／背后关联”和“暗示程度”；schema 中伏笔只有 `title` 和自由文本 `body`。
- 建议：把这几项并入伏笔条目的设计字段，或至少作为 Agent 生成伏笔候选时的固定模板。其中“表面线索”和“背后关联”分开存放，也为 S15 的信息最小化提供依据。

**S8 已过章节数**（原 3.3、4.3）
- 原始：伏笔模块展示埋设章节、回收章节、已过章节数，由程序计算，章节重排后按同一口径重算。
- 现状：Proposal 目标 4 要求发现“超期未回收”，第 2 节有“允许延迟范围”，但没有任何计数机制，超期无从判断。
- 建议：把“已过章节数”作为派生指标（不是第五种状态）。需要确认两点：
  - 新设计中章节顺序来自线路规划，而伏笔状态跨方案汇总，所以计数必须指定按哪个方案的哪条固定线路计算；
  - 原始设计遗留的计数起止、终点口径（规划推进章还是正文完成章），以及回收后如何展示。

**S9 状态只能通过标记改变**（原 4.2）
- 原始：AI 读取程序生成的状态和计数，不直接填写派生字段，不开放任意状态字段写入；读取或编辑规划内容的权限不等于伏笔状态写入权限。
- 现状：Proposal 的“模块 Agent 的权限与职责”写有“推进状态”“状态更新”，与“状态只从标记派生”存在歧义。
- 建议：明确 Agent 只能通过增删改正式标记间接改变伏笔状态，不存在直接写状态的操作。

**S10 读取派生状态以调整伏笔建议**（原 2.5）
- 原始：foreshadowing 读取程序维护的现有状态，辅助调整建议。
- 建议：在模块 Agent 的伏笔提议能力中写明依据包括当前派生状态和已过章节数，例如对长期未回收的伏笔优先给出回收建议。

### 模块 Agent

**S11 按任务范围授权**（原 5）
- 原始：授权按任务范围生效。例如用户要求“将这一卷拆成十章并创建对应条目”后，Agent 可在范围内连续新增和修改；超出范围的调整需说明并另行取得授权。
- 现状：新设计按模式划分审批，自动模式对全部模块内非删除操作持续授权，没有“不超出本次任务范围”的约束。
- 建议：自动模式也以当前用户指令为操作范围，超出范围的改动需说明后另行确认；讨论模式中，用户的明确指令可作为一个批次的确认范围。

**S12 模块配置与分开的变更记录**（原 5）
- 原始：规划 Agent 可读取、在授权内修改大纲规划模块的配置；条目变更和配置变更分别记录。
- 现状：新设计没有“模块配置”这个对象。
- 建议：可选。如确有模块级配置（如默认篇幅、标签、默认模式），纳入 manifest 并单独记录变更；没有则不补。

### 界面

**S13 条目与节点的展示内容**（原 3.1、3.2）
- 原始：细化完成后，可在同一条目中查看细纲及其标注；故事线节点展示编号、标题、层级和细化情况，并可打开条目详情。
- 建议：大纲库中章节大纲详情可同时查看其细纲；线路节点显示关联条目的层级和细化情况（是否有正式细纲），便于判断能否固定。

**S14 便于人读的编号**（原 2.5、3.1）
- 原始：条目和伏笔有编号，供引用和识别。
- 现状：新设计使用 `fo-xxx` 等稳定 ID 和 slug。
- 建议：可选。如用户需要在对话中说“伏笔 F-12”，可增加显示用短编号，但不替代稳定 ID。

### 与 writer.pro 的交接

**S15 只交接本章需要的伏笔信息**（原 2.1、2.3）
- 原始：需要呈现的伏笔由上游落实到细纲与指导，writer 不需要管理规划账本，也无需解读后续完整的伏笔规划。
- 现状：Proposal 第六节写 writer.pro 读取“正式伏笔标记”；当前实现 `server/outline/writer-context.ts` 会把固定线路涉及的伏笔**定义**一并交给正文侧。伏笔定义包含回收意图，可能让正文提前泄露后续剧情。
- 建议：交接只包含本章标记的文本和由细纲、写作指导落实的呈现要求，不包含伏笔定义中的背后关联和回收计划。

## 3. 已被新设计取代、不需要补充的内容

| 原始设计 | 新设计 |
| --- | --- |
| 待埋设／待回收／已回收三状态 | 草稿／待使用／已埋设／已回收四状态 |
| 细纲写回对应大纲条目 | 细纲为依托章节大纲的独立文件 |
| 故事线只纳入已确认使用的条目 | 线路中固定的节点构成正式线路 |
| 按 Agent 列出的权限表 | 讨论／自动模式与删除审核 |
| 不把 UI 编排设为细化任务的强制前置 | 细化仍不需要线路；但正文写作只读固定线路，按新设计执行 |

## 4. 现有实现中因误读产生的偏差

以下内容本文不作处理，是否回退由开发者决定。

模块本体基本忠实于新 Proposal，包括 `server/outline/`、大纲 HTTP 路由、规划工具、唯一的模块 Agent `outline.planner`、工作台 UI 和伏笔标记。代码中没有独立的 outline、Detailed outline、foreshadowing Profile，也没有旧三状态或章节计数器。偏差集中在下面几处。

**D1 把现有 `writer` 当成 `writer.pro` 改造**（t09）
- 改动，路径相对 `packages/neuro-book/`：
  - `assets/workspace/.nbook/agent/profiles/builtin/writer.profile.tsx` 移除 bash，改为暴露 `get_fixed_outline_context`，提示词同步修改；
  - `server/agent/tools/file-tools.ts` 在通用文件工具中硬编码 `profileKey === "writer"`：禁止读取 `outline/`、`.nbook/`，写入只允许 `manuscript/*.md`，并禁止 writer 调用 bash；
  - 新增的 `server/agent/tools/writer-outline-tool.ts` 只允许 `writer` 调用；
  - `server/agent/profiles/builtin-contracts.ts` 新增 `fixedOutline` payload；
  - `assets/workspace/.nbook/agent/workflows/chapter-write-review-revise/workflow.ts` 把 `fixedOutline` 设为**必填**，缺失即报错；
  - 写作 smoke 脚本、`writer-profile-contract.test.ts` 同步修改；`docs/specs/outline/writer-handoff.md` 也把这些改动记为 `writer.pro` 的实现。
- 可以保留的部分：`server/outline/writer-context.ts`、`writer-materials.ts` 的只读投影本身符合 Spec，只是调用方被绑到了现有 `writer`，可留待 writer.pro 接入。
- 影响（从代码推断，未运行验证）：
  - 现有 writer 不能再用 llmlint；
  - 章节写入路径不在 `manuscript/` 下的写作会被拒绝；
  - 没有大纲规划模块固定线路的项目，无法运行现有的章级写作评审 workflow。
- 与原始设计冲突：原始设计规定 writer.pro 是新 Agent，“不直接继承现有 writer 中主动查询 Plot、查证世界状态、理解规划账本和阅读大量工作区手册的要求”。

**D2 把设计文档当成用户数据来迁移**（t10、`docs/specs/outline/migration.md`、`server/outline/migration.ts`、迁移 HTTP 路由）
- 该能力把 Project 内的 `新小说编写计划.md` 当作“旧规划文档”导入 `outline/`。实际上它是开发设计文档，原始模块从未实现，不存在需要迁移的用户数据。Proposal “规范来源”一节、ADR 0022 第 9 条和 Proposal 待决问题第 21 条都把两件事混在了一起。
- Proposal 中“已有普通笔记中的大纲、细纲和伏笔可渐进导入”是另一项独立需求，是否保留需要单独确认。

**D3 改写了 `新小说编写计划.md`**
- 工作区中该文件删除了原始的大纲、细纲、伏笔设计，与 Proposal 自称的“原文件保留且不被覆盖”矛盾。
- 同时删掉了 writer.pro 的关键约束，即“现有 writer 的复杂上下文不作为新 Agent 必须继承的结构”和“不直接继承现有 writer……”两句。
- 改写后 writer.pro 的输入来源、权限等已按新模块调整；这部分方向正确，但应恢复被删掉的约束。

**D4 Proposal、ADR 和 Spec 中的替换关系表述**
- Proposal 写“旧文档只作为 `writer.pro` 的下游交接说明”，没有说明其余部分仍需按原始设计开发。
- `writer-handoff.md` 等 Spec 把 `writer.pro` 当作已存在的 Profile 编写验收条件。

## 5. 开发者决定（2026-09-26）

1. 三个 Agent 作为大纲规划模块主 Agent 的专用子 Agent 实装，用于处理专业问题，例如大纲问题交给 outline。设计见 Proposal “模块 Agent 的专用子 Agent”一节。
2. S1–S15 按本文建议处理：
   - S12（模块配置）和 S14（显示用短编号）暂不补；
   - 其余写入 Proposal “原始设计补充”一节和对应 Spec；
   - S3：“待补”不阻止正式采用，但作为告警传递；
   - S8：按方案、按固定线路的章节顺序计数。
3. D1–D3 的处理：
   - 回退对现有 `writer` 的改造；
   - 删除迁移功能；
   - 恢复 `新小说编写计划.md` 原文。

   D4 的相关表述已随 Proposal、ADR 0022 和 Spec 一并修订。
